# How it was tested

[← README](../README.md)

Numbers below are for commit `957345c` (12 October 2026), unless a later date is given.

- **Test gate.** `go build ./... && go vet ./... && go test -race ./...` passes.
- **Mutation testing** (1–2 November 2026, on the code of v0.4.0). 650 bugs injected one at a time (`scripts/mutations/`), and every one of them makes a test fail: store and proofs 412, collector and intake 85, keyring 62, evidence log 21, gateway journals 15, chain 18, TSA 14, configuration 17, copy transport 6. In the first run two of them survived and one did not compile. Since a head is the root of a tree over the links, a replaced link breaks that root as well, and the test of the check that each link refers to the hash of the one before saw it only through the root; the test now builds a chain whose tree, time-stamps and signed head agree, so that only that check refuses it. A test of the collector's head files lost its premise when the collector began to set aside, at start, a head journal it cannot read, and nothing checked that `checkpoint.json` is written before the journal; the test now breaks the journal after the first start. The mutation that did not compile is fixed (P-38 and P-39 in [`docs/dev/FINDINGS.md`](dev/FINDINGS.md)). The last fix of the collector (P-42, P-43) came after the full run: the five mutations it added or rewrote are caught, and 39 of the collector's other 106 mutations, run again on the final code, are caught; the rest were not run again. Four mutations are caught only because the tests run out of their 10 minutes: one makes every copy pass send everything again, and under three a test of the receive-time clock waits without a deadline instead of failing (P-41). On the code of v0.3.0 (28–29 October) there were 578, and six of them survived the first run: what they broke (the shape of the chain after a crash and around a time-stamp, receive times around a time-stamp and after a host clock step) no longer carries the promise check, and the tests saw it only through that check; tests now read it from the chain itself (Q-84 in [`docs/dev/FINDINGS.md`](dev/FINDINGS.md)).
- **Mutation testing since v0.4.0** (7–8 November 2026, the subject labels and their move to month keys, then the witness check by receipt time). The set has grown to 873 injected bugs. Those written for the new code were run as it was written; a few survived at first and were closed with a test, or removed as equivalent with the reason recorded in the set. The 74 that guard the last of the subject-label changes were run again on commit `5e24589`, and every one makes a test fail; so does each of the 59 added with the witness check by receipt time and the 3 older ones it rewrote, run on the code of commit `90d815b`. The whole set of 873 has not been run together since v0.4.0: of the older mutations in the files this work touched, only part were run again.
- **Mutation testing of the cosigning witness** (8–9 November 2026). 128 bugs injected one at a time into the C2SP witness, the store's side of it, the bundle check and their configuration (`scripts/mutations/cosign.json`), and every one makes a test fail. The first run, 78 of them on the first commit of the feature (`cda358d`), found 8 that survived and 7 that did not compile: a base64 newline that `encoding/base64` lets through even in strict mode, a verifier key whose type byte and key ID disagree, a 33-byte proof line, the witness without one lock over the check and the write (the concurrent requests did not overlap until a test made them arrive together), and four whose tests refused for another reason or were masked by another check; tests now close each (P-111 in [`docs/dev/FINDINGS.md`](dev/FINDINGS.md)). The format mutations were run again on commit `07454ef`, the rest on the code after the review (`1c13d6b` and the three tests that closed its last three survivors). After the second review (9 November) the whole set, grown to 128, was run on the final code: 122 were caught, and the 6 that survived were tests that lost their point when the code changed — the same head sent again is no longer written, a damaged line no longer hides the order of the index, a repeated key is now caught by another check — or a case seen only in the log; tests now close each (P-126…P-129). The store's side runs its tests with `-run Cosign` first, and a mutant that survives that is run against all the packages of the set. When single-record bundles began to carry a second cosignature of each key (P-135), the 11 mutations of how the store picks cosignatures for a bundle were run again, and every one makes a test fail.
- **Mutation testing of TSA revocation and the second TSA** (9 November 2026). 36 bugs injected one at a time into the revocation rule (`internal/tsa`), its use in the three kinds of bundles, the second TSA of the store, its configuration and the `esverify` flags (`scripts/mutations/tsarevoke.json`), and every one makes a test fail; three that did not compile at first were rewritten. The review that followed (P-132…P-140 in [`docs/dev/FINDINGS.md`](dev/FINDINGS.md)) added 33 for what it fixed: the kinds and scope of CRLs, all the CRLs of a CA together, certificates that expired, the key a compromise covers, the auditor's list, the witness for T2 and the journal of the second TSA. The set of 69 was run on the final code, without the race detector, and every one makes a test fail. The second review of those fixes (P-141…P-148) added 17 more and rewrote 11 for the new code; of the 86, run on the final code, 82 were caught at once, one survived (a revoked certificate's time-stamp taken for a clean one still waited for a proof under the new rule on keys, and only the reason in the report differed; a test now requires that reason) and three did not compile; those four, fixed, are caught. The third review (P-149…P-156) found the same class again, and the check was redesigned around one assessment per bundle; the set was rewritten for it: 24 mutations moved to the new code, three retired with the code they covered and 12 added for the new rules. Of the 95, run on the final code, 92 were caught at once; two survived because no test covered them (a root's own compromise on the auditor's list, the order of a CA's two certificates in a token) and one did not compile. With the two tests added and that mutation fixed, all three are caught. The first review of the redesign (P-157…P-174) moved 14 mutations to the new code and added 20 for what it fixed (the release of a hold, a CRL under a new key of its CA, certificates outside the chains, a CA certificate revoked with no reason, a proof of existence only from a time-stamp whose own revocation was checked, broken PEM boundaries, an extension given twice, the signer of a token that does not carry its certificate); of the 115, run on the final code without the race detector, 111 were caught at once and four did not compile (each mutation left a variable unused); rewritten, they are caught. The store's side runs its tests with `-run 'Archive|Cosign|WitnessRescues'` first, and a mutant that survives that is run against all the packages of the set.
- **The cosigning witness end to end** (9 November 2026). The real binaries — `evidencestore serve`, `eswitness serve` over HTTP, `escollect`, `esverify -witness-key` — on one machine: a bundle verifies with the witness's key and fails without the cosignature or with another key of the same name; the witness restarted and the store killed with `kill -9` both go on cosigning, and bundles made before and after verify. After the self-review (P-108, P-109), a review by two researchers and a black-box tester found eight serious defects (P-112…P-119: the witness's refusal journal, the note it serves, what to do when its state is lost, the store not noticing that loss, heads behind the copy, cosignatures missing from the copy, a witness clock that ran ahead, a key file shadowing `-witness-key`), all fixed with tests.
- **Simulations:** randomized scenarios checked against an oracle (commands under Development).
  - Store with crashes: 2,000 scenarios of 300 steps, no failures. They went through 36,038 crashes (3,848 in the middle of a write), 6,649 restores from the copy (1,154 after the disk was lost in the middle of a copy pass), 1,368 disks that lied about fsync, 2,185 destroyed keys (231 crashes in the middle of a root rotation) and 75,858 rounds of parallel intake (1.25 million batches, 312,900 pairs of identical concurrent requests). 300 more scenarios under the race detector found no data race. Later, on 17 October, CI caught a data race in the simulation's own bookkeeping (test code, not the store); it is fixed (Z-12 in [`docs/dev/FINDINGS.md`](dev/FINDINGS.md)).
  - Receive-time clock: 3,000 scenarios, no failures.
  - Collector: 2,000 scenarios in each of four worlds (one file or a glob, with and without destruction) against an in-memory store, 150 per world against the real store over mTLS, and 400 per world against the real store with all faults at once; no failures.
  - On 27 October, on the code of the bundles over a window of time: store with crashes 1,500 scenarios of 300 steps and the receive-time clock 2,000 scenarios, no failures; the collector 2,000 scenarios in each of four worlds and 200 per world against the real store, with one failure in a world with destruction (a gap the collector left reached the store only with the next record; fixed the same day: the heartbeat carries the last issued number, and the scenario passes).
  - On 27 October, evening, after the third review round: store with crashes 1,500 scenarios of 300 steps and the collector 2,000 scenarios per world and 200 against the real store, no failures; the receive-time clock run of 2,000 scenarios failed 226 on a fault in the simulation's own check (two time-stamps in one second after a restart), and after that was fixed 300 scenarios ran with no failures. A new simulation of a dishonest store owner (`TestOwnerSim`: held-back records and tokens, copies of old tokens, links dated back as far as the checks allow, shifted receive times) found that a receive time shifted forward hid a record from the window bundle with its promise kept; the collector now checks receive times.
  - On 28 October, on the code of v0.3.0, with the collector's promise checked against the time-stamps: store with crashes 2,000 scenarios of 300 steps, through 37,307 crashes (4,186 in the middle of a write), 6,727 restores from the copy (1,104 after the disk was lost in the middle of a copy pass), 1,395 disks that lied about fsync, 1,322 destroyed keys (138 crashes in the middle of a root rotation), 75,653 rounds of parallel intake (1.25 million batches, 313,129 pairs of identical concurrent requests) and 56,296 episodes of a lost collector; a dishonest store owner 2,000 scenarios, in which each of the 632 window bundles that left a record out was exposed by that record's promise; the receive-time clock 1,000 scenarios; the collector 2,000 scenarios in each of four worlds and 150 per world against the real store; no failures. On the release candidate with test hooks: an upgrade from v0.2.0 with `kill -9` during intake (all 632 promises verify) and an evidence log whose fsync fails (no time-stamp until restart, then all 244 promises verify).
  - On 1–2 November, on the code of v0.4.0 (a tree over the links, the encrypted copy, collectors as witnesses of the heads): store with crashes 2,000 scenarios of 300 steps, through 37,294 crashes (4,191 in the middle of a write), 6,735 restores from the copy (1,102 after the disk was lost in the middle of a copy pass), 1,396 disks that lied about fsync, 1,322 destroyed keys (139 crashes in the middle of a root rotation), 75,647 rounds of parallel intake (1.25 million batches, 313,063 pairs of identical concurrent requests) and 56,128 episodes of a lost collector; a dishonest store owner 2,000 scenarios, in which each of the 632 window bundles that left a record out was exposed by that record's promise; the receive-time clock 1,000 scenarios; the collector 2,000 scenarios in each of four worlds and 150 per world against the real store, in which no collector found a head that did not extend the last one it had accepted, and after the last fix of the collector 500 per world and 150 per world against the real store again; no failures. The demo passes.
  - On 8 November, on commit `5e24589` (subject labels by month key, a month whose key is closed sent as leaves): store with crashes 120 scenarios of 200 steps, a dishonest store owner 300 scenarios, the receive-time clock 200 scenarios, the collector 150 scenarios in each of four worlds against an in-memory store; no failures. These runs are shorter than the ones above, which have not been repeated on this code. `scripts/demo.sh` and `scripts/demo-intruder.sh` pass.
- **A model of an AI agent's log** (7 November 2026; synthetic data shaped after public descriptions of a retail bank assistant; one machine with 12 threads and NVMe, store and collector on it, mTLS over localhost). On the code of v0.4.0: a month of traffic, 794,565 records, went in within 296 seconds (2,687 records a second) and took 458 MB on disk. The store's signed receipt reached the collector in 0.54 s (median) and 1.04 s (99th percentile) at the modelled pace, 0.66 and 1.19 s at ten times that pace, 5.8 and 7.8 s at 2,179 records a second. `kill -9` of the store for a minute and of the collector at ten times the pace lost none of 39,941 lines and repeated none, and 40 `kill -9` at full speed left all 281,520 records in place. On the code with subject labels, before they moved to month keys: a bundle for one client out of a burst of 57,160 records, with 18,935 records of 799 clients in the window, opened that client's 75 records and no others; it took up to 2.5 s to build, under 2 s to verify, and came to 48 MB, since the encrypted evidence of every record of the window travels whole. With every model call writing a 100 KB prompt, records averaged 18.7 KB, the disk took 1.02 times the input (2.28 times at 267 bytes a record), intake ran at 360–410 records and 4 MB a second on a loaded machine, and the same kind of bundle over a window of 5,815 records came to 156 MB, about 145 of them the closed evidence of other clients. Not tried: a real network, power loss, production hardware, real traffic.
- **Live gateway.** `scripts/demo-pipelock.sh` passes against Pipelock v3.6.0 built from the tag's commit.
- **A night on real data** (11–12 October, 21:19–06:23). The store ran with four collectors: the host's own `/var/log/syslog`, `auth.log` and `kern.log` (read from the start), and the flight recorder of a live Pipelock v3.6.0 that blocked an "agent" all night (no request left the host). During the night logrotate rotated all three logs at midnight (`create`, `delaycompress`, rsyslog HUP), the store was restarted 5 times, a collector was killed with `kill -9`, Pipelock was restarted twice (3 sessions, 359 shards), and the copy went to a directory every minute. Every one of the 104,738 records matched its source line, in order, with no duplicates and no losses: syslog 71,120 (67,596 from the rotated file, 3,524 from the new one), auth.log 1,246, kern.log 10,752, Pipelock 21,620. A sample of 7,560 proof bundles across the whole range verified the way `esverify` does, the Pipelock ones with the gateway's checkpoint signature. A store restored from the copy (76 MB, chain checked up to signed head 8005) gave the same result. The store log had no errors. The scripts of this run were a one-off and are not in the repository.
- **Witness and copy on real S3** (25 October, MinIO RELEASE.2025-10-15 with Object Lock in compliance mode). The store sent its signed heads to a locked bucket and its copy to another; `esverify -heads` verified a bundle against all versions of the witnessed heads, a junk version and a delete marker put over a head afterwards changed nothing, and `restore` from the copy passed. A one-off run; AWS itself was not tried.

## Simulations

```sh
SIM_SEEDS=1000 go test -timeout 0 -run TestCollectorSim ./internal/collector/   # collector simulation: rotations (dateext too),
                                      # renames, restarts and crashes before, after and in the middle of a write, long lines,
                                      # lost store answers, permissions, destruction — every line once, or a visible gap
SIM_REAL_SEEDS=100 go test -timeout 0 -run 'TestCollectorSim/real' ./internal/collector/ # the same against the real store
                                      # over mTLS: every record's proof verifies, every gap is a chain event
CLOCKSIM_SEEDS=1000 go test -timeout 0 -run TestClockSim ./internal/store/       # receive-time simulation: clocks off, drifting,
                                      # jumping; slow, absent TSA; idle days; a suspended host; a record still
                                      # being written while a time-stamp is taken — every accepted record verifies
                                      # and keeps its promise
ADVSIM_SEEDS=1000 go test -timeout 0 -run TestOwnerSim ./internal/proof/         # a dishonest store owner: held-back records and tokens,
                                      # copies of old tokens, backdated links, shifted receive times, long
                                      # deadlines — every record of a window is in each window and one-source
                                      # bundle that verifies, or its promise shows the missed deadline
STORESIM_SEEDS=1000 go test -timeout 0 -run TestStoreCrashSim ./internal/store/  # store crashes at every write point (chain leaves,
                                      # link, head; key backup; root rotation; before the answer; torn writes), keyring.dat
                                      # restored from backup, key destruction, segment rotation, a disk that lies about
                                      # fsync, disk loss and restore from the copy (also mid-copy), a restart minutes
                                      # after the crash, parallel intake with
                                      # duplicate requests — every promise kept, every record once, every gap in the chain,
                                      # everything copied by a finished pass back after a restore
```

`go test` runs the simulations with a few dozen scenarios each; a failure prints `SIM_SEED=` (`CLOCKSIM_SEED=`, `ADVSIM_SEED=`, `STORESIM_SEED=`), which replays that scenario with its full trace (a store scenario with parallel intake replays its steps, not the exact interleaving). Every collector scenario draws its own set of faults; `SIM_FAULTS=all` (or a comma list: `long,after,torn,flaky,perm-new,perm-file,perm-dir,perm-spool,dateext`) fixes it.
