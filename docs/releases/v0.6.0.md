evidencestore is an independent witness for logs. A collector next to the log sends every line to a store on another machine, and the store can later prove any of those lines to an auditor, offline and without being trusted: the exact bytes, their place in a hash chain, a signed chain head and RFC 3161 time-stamps from before and after the record. Retention works by destroying a month's key: the bodies become unreadable in every copy, while the chain and the proofs stay valid.

This release turns to AI agents. Any gateway can sign a receipt for every step of what its agent does, and the store checks it at intake; the collector reads a PostgreSQL database by logical replication and keeps the agent's transactions whole; an MCP server runs the agent's SQL under limits; an operator undoes an agent's transaction from what the store holds; and people get alerts. It reads a `data_dir` of v0.5.0 as it is, and collectors of v0.5.0 work with it unchanged. It also fixes a defect of the collector that is in v0.5.0: see Fixed.

## New in this release

- **Gateway receipts.** Any gateway can write one signed JSON line per step of an agent's action (`receipt/v1`): the gateway, a sequence number and the hash of its previous receipt, the time, the action and the step, references to the records it touched elsewhere, an approval as it was received (a customer's mandate, say), the body, and an Ed25519 signature over it all. A source with `"content_type": "receipt/v1"` and the gateway's `gateway_key` has every line checked at intake — the format, the signature, the link to the gateway's previous receipt — with a verdict next to it in the chain; nothing is rejected. A bundle for one action opens its receipts and keeps the others closed, and `esverify -gateway-key` checks the signature of every open receipt and the gateway's chain across the window, so a closed receipt between two open ones was neither left out nor swapped. `esreceipt` (`keygen`, `sign`, `verify`) is for gateways not written in Go ([Gateway receipts](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/receipts.md)).
- **An action across sources.** `esverify -proof receipts.json -linked tx.json` checks the bundle of an action's receipts together with the bundles of the subjects its receipts name in other sources, such as the transaction it made in a database: each by its own rules, every receipt of the action open, and every subject named in a linked bundle over the same window with all its records open.
- **Evidence for purchases made by AI agents.** The receipts a platform signs for every step of a purchase (mandate, cart, payment, delivery), one purchase as a bundle with the other purchases closed, and a report of it for a dispute that checks the customer's signature on the mandate (a compact JWS with ES256) and compares the cart with what was signed (`scripts/demo-purchase.sh`; [Purchases](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/purchases.md)).
- **PostgreSQL, an MCP server for an AI agent, and undo** ([PostgreSQL and an MCP server](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/postgres.md)):
  - `escollect` reads the database's log itself, by logical replication (`pgoutput`, PostgreSQL 14 or newer), and every transaction on the tables you name reaches the store, whatever role it ran under. A transaction named in a signed intent of the gateway is kept whole, with the rows before and after; any other is kept as a fingerprint: row keys and hashes, no rows. The database is observed, not changed: no triggers or markers in it. A database restored from a copy, a dropped or moved slot and missing receipts are named.
  - `esmcp`, an MCP server, runs the agent's SQL in its own transaction under its own role, writes the signed intent before the SQL and the outcome after, and stops an action over its limits before commit: rows per action, rows per window, actions per minute, a statement timeout.
  - `esundo` undoes an agent's transaction from the rows the store holds: it fetches and verifies the bundle itself, compares every row with the database and applies the undo in one transaction, recorded as an action of its own. The agent can be given the same as MCP tools.
  - Alerts reach people in Telegram, through Slack-compatible webhooks or at an address of your own: a change past the gateway, a mass change, a canary row touched, a database restored from a copy, missing receipts, an action refused.
- **One collector, several sources.** A `sources` list in the collector's config, each source with its own certificate, spool and input (`file`, `glob` or `postgres`); a config without it is one source, as before.
- **Docker.** A `Dockerfile` and `compose.yaml` run PostgreSQL, the store, the collector and the MCP server on one machine as a trial; the first start makes the certificates, keys and passwords.

## Fixed

This defect is in v0.5.0.

- **A long line without its line break filled the collector's memory.** The file input read a line whole and, while its line break had not been written, read it again on every pass: 400 MB without a line break took 1.7 GB of memory, and under a memory limit the collector restarted in a loop together with every other source of the process. Now a long line goes in pieces the size of the largest body, from its start, each as soon as the file holds a byte after it; the records are the same as before.

## Compatibility

- A `data_dir` of v0.5.0 is read as it is. The intake protocol is unchanged: collectors of v0.5.0 work with this store, and this release's collector reads a config of v0.5.0 as it is.
- The bundle formats are unchanged. An older `esverify` reads this release's bundles of a receipts source by the store's verdicts alone: it does not check the receipts' signatures itself (it refuses `-gateway-key` for them) or link the gateway's chain, and it names receipts in the words of the Pipelock journal. Use the `esverify` of the same release as the store.
- New and optional: sources with `"content_type": "receipt/v1"`, the collector's `sources` and `postgres`, and three binaries, `esreceipt`, `esmcp` and `esundo`.
- No new dependencies: the PostgreSQL protocol and its logical replication are implemented in the repository.

## Known issues

- **The Docker files have not run under Docker.** The first-start script, the configs, the roles' login by password, the database setup run twice, an action through the MCP server and an undo with `esundo` were run outside Docker; `docker compose up` and the images themselves were not.
- **What the PostgreSQL path promises rests on a trust boundary:** the gateway's key out of the agent's reach, the receipts directory and the collector's state written only by the gateway and the collector, a restore of the database from a copy known to people. Whoever writes the receipts directory without the key cannot forge a receipt, but can take lines out and put them back, or get around the MCP server's limits before commit ([The trust boundary](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/postgres.md#the-trust-boundary)).
- **The MCP server's limits stop only actions that go through it.** A change made past it is seen after commit, as a fingerprint and, with `require_gateway`, an alert.
- **AP2 v0.2 mandates are kept, not checked.** AP2 v0.2 carries its mandates as chains of SD-JWTs, on a draft that is still changing; the purchase report checks a compact JWS only. The store keeps every mandate byte for byte, so it can be checked later.
- **Erasure stays per source and month**, also for the full rows of an agent's transactions, which are personal data; and a bundle grows with the whole source in its window, not with one action or purchase.
- From v0.5.0: the seal on the store key checks RSA and ECDSA with SHA-2 only (no ГОСТ); cosignatures are Ed25519 only.

All of them, with their causes: [Known limitations](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/limitations.md) and [PostgreSQL, Limits](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/postgres.md#limits).

## Install

Binaries: `evidencestore`, `escollect`, `eswitness`, `esmcp` and `esundo` for Linux amd64 and arm64; `esverify` and `esreceipt` also for macOS (amd64, arm64), and `esverify` for Windows (amd64). Check them before use:

```sh
sha256sum -c SHA256SUMS --ignore-missing
gh attestation verify esverify-linux-amd64 --repo Nikolay1994Kaz/evidencestore
```

With Go 1.25.4 or newer: `go install github.com/Nikolay1994Kaz/evidencestore/cmd/esverify@v0.6.0`, likewise `cmd/evidencestore`, `cmd/escollect`, `cmd/eswitness`, `cmd/esreceipt`, `cmd/esmcp` and `cmd/esundo`. In Docker: `docker compose up -d` in a clone of the tag ([Try it in Docker](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/postgres.md#try-it-in-docker)); no image is published.

Setting up a store, collectors and a witness, with systemd unit files: [README, Install](https://github.com/Nikolay1994Kaz/evidencestore#install).

## How it was tested

- The test gate with the race detector, in CI on Go 1.25.4. The gate now also builds `esverify` for Windows and macOS and `esreceipt` for macOS: the release build had been broken on Windows since the receipts code came in, and this was found while preparing this release.
- The PostgreSQL path: live tests against PostgreSQL 16, restores from a copy included, and `experiments/pg-undo/run.sh` end to end, with a window bundle and a bundle over one action with its transaction.
- Review rounds by AI agents, each followed by passes over the fixes: the findings and their fixes (P-231 to P-385) are in [`docs/dev/FINDINGS.md`](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/dev/FINDINGS.md), in Russian. The rounds stop at a written rule: what needs the trust boundary broken is a limit, not a defect, and the next round comes after a large piece of new code or before the first pilot.
- Mutation testing. The set of injected bugs grew from 1,157 to 1,301. The ones written for the new code (gateway receipts 28; the PostgreSQL path 32, 32, 27 and 25) were run as that code was written, and on the release code every one of the last set makes a test fail. 33 mutations of six earlier sets no longer match the code that later rounds rewrote, and they have not been rewritten; the whole set has not been run together on this release's code.
- Simulations on this release's code, short runs, no failures: the store with crashes, 120 scenarios of 200 steps; a dishonest store owner, 300 scenarios; the receive-time clock, 200 scenarios; the collector, 150 scenarios in each of its worlds against an in-memory store. The long runs made for v0.4.0, thousands of scenarios each, have not been repeated on this code.
- The demos `demo.sh`, `demo-intruder.sh` and `demo-purchase.sh` pass on this release's code; the Pipelock one was not run again.

Details: [docs/testing.md](https://github.com/Nikolay1994Kaz/evidencestore/blob/v0.6.0/docs/testing.md).

## Before you use it

- Until 1.0 the on-disk formats (evidence log, chain, keyring) may change; each release will describe the way over.
- The pilot cryptography is not certified: AES-256-GCM from the Go standard library, root keys in files. The root store is a plug-in point for an HSM.
- The PostgreSQL path is new: start with the Docker trial and read its trust boundary and limits.
- Read [Known limitations](https://github.com/Nikolay1994Kaz/evidencestore#known-limitations).
