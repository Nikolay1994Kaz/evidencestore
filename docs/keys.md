# Keys and retention

[← README](../README.md)

Month keys live in `keyring.dat`. It is encrypted under a fresh file key on every write, and only that 32-byte file key is wrapped by the root key in `roots_dir`, so the root can move into an HSM or a KMS unchanged. Three places matter:

- `keys.backup_dir` receives a copy of `keyring.dat` after every change. A new month key is not used until that copy has landed, so losing `data_dir` never loses a key that sealed a record. The copy is useless without the root. It also holds `sign.key` and `copy.key`, the key of the remote copy's chunks ([Copy and restore](copy-and-witness.md#copy-and-restore)): nothing is copied before `copy.key` has landed there, a different `copy.key` found there is never overwritten (`evidencestore_copy_key_backup_pending` until a person decides which one is right), and a store whose chain and copy exist does not make a new one when `copy.key` is missing from `data_dir`.
- `keys.roots_mirror_dir` is a second copy of the roots on another disk or machine. Every root is written to both places and destroyed in both; a missing copy of the current root is restored at start and every minute, and a damaged copy is bypassed when reading. A missing mirror directory is never created, by `init` either (it looks like an unmounted disk): create it yourself. An unreachable mirror does not stop the store, but destruction is not final until both directories can be listed (`roots_unreachable` in `status`). Without a mirror, losing `roots_dir` makes every stored body unreadable for good; the chain and the proofs survive.
- The subject labels of a source with `subject_field` (see [One subject](bundles.md)) come from a label key that each month key derives (HKDF), so destroying the month key destroys its labels too: no one can compute them any more, the store included. While a month key awaits destruction the store derives nothing from it, but the key is still in `keyring.dat` and in the backup: a cancelled destruction brings back the same labels, as it brings back the bodies.
- Every change of a month key's state — deactivated, awaiting destruction, a cancelled destruction, destroyed — is a receipt in the chain once the change has reached the backup, and the next TSA time-stamp certifies it. Only awaiting destruction (until it is cancelled) and destroyed close a month: the store deactivates every past month a few minutes after it ends, and a deactivated key still opens bodies. A window bundle over that time (`evidencestore proof -window -from -to`) carries the receipt, and `esverify` lists it with its link and operation. While a month key lives, a fresh bundle tells a closed month from a month whose evidence someone took out of a bundle; once the key is destroyed, the receipt is what is left (see [What opens](bundles.md)). It is the store's own statement, and a bundle does not carry the time it was issued.
- Nothing else may hold a copy of `roots_dir` or of the mirror. An old root copy plus an old `keyring.dat` still opens a destroyed key, so destruction is only as final as your control over those copies. The config check rejects layouts where one directory would hold both `keyring.dat` (or its backup) and a root.

The waiting period before a key is destroyed (at least `keys.min_wait`, which outside a demo stand is one hour or more, and at most ten years) starts at a TSA time-stamp taken with the request, and it ends by the store clock and by a fresh TSA time-stamp, whichever is earlier: a host clock that is behind at request time or moved forward later does not shorten it, and without a time-stamp destruction waits. The time-stamp lands in the chain before the destruction receipt.

`init` refuses to run when `keys.backup_dir` already holds `keyring.dat`, `sign.key` or `copy.key`: that is what a store that lost `data_dir` looks like, and a fresh keyring would overwrite the keys of every month. Put `keyring.dat` back into `data_dir` and `sign.key` into `data_dir/chain/` instead. The store, for its part, makes a new signing key only for an empty chain and when `keys.backup_dir` holds none: without `data_dir/chain/sign.key` it refuses to start while the chain holds links, while the backup holds a key (the error names the file to copy), or while the backup cannot be read. A different `sign.key` in the backup stops the start while the chain is empty; with a chain the store starts and raises `evidencestore_sign_key_backup_pending`. The backup copy is never overwritten. The backup also remembers the generation of `keyring.dat`, so an older file (a disk rolled back) never overwrites a newer backup.

A key state change enters the chain only after it has reached `keys.backup_dir`. If the backup is down, the change still takes effect, the operator gets an error saying the copy is pending, and the store retries every minute; `status` shows `keyring_backup_pending` meanwhile.

`status` also lists `orphan_roots`: roots that `keyring.dat` does not know. They appear after a crash in the middle of a key rotation, or after `keyring.dat` was restored from a backup older than the last rotation. In the second case an orphan can still open an old `keyring.dat` from the dead machine, so destruction is not reported as final (`destroyed-effective`) while orphans exist. Remove them with `evidencestore keys destroy-orphan-roots`, but only if `roots_dir` is not shared with another store.
