# Опыт: откат одного действия агента по до-образам из хранилища

Ветка-опыт, не продукт. Вопрос был один: ложится ли связка «аудит + откат» на
хранилище как оно есть. Код хранилища, сборщика и `esverify` здесь не изменён
ни строкой; всё новое лежит в этом каталоге.

```
Postgres (wal_level=logical, REPLICA IDENTITY FULL)
  → pg_recvlogical + wal2json   каждое изменение строки — строка JSON в файле
  → escollect                    читает файл как обычный журнал
  → evidencestore                источник с "subject_field": "xid": метка записи — номер транзакции
  → proof -subject <xid>         все до-образы одной транзакции одним проверяемым пакетом
  → esverify -bodies             тела байт в байт, только из пакета, прошедшего проверку
  → undo.py                      обратные операции, сверка с базой, одна транзакция отката
```

## Запуск

```
ES_BIN=/путь/к/бинарникам experiments/pg-undo/run.sh     # около двух с половиной минут
ROWS=150000 EDGES=0 ES_BIN=… experiments/pg-undo/run.sh   # замер объёма
python3 -I experiments/pg-undo/test_undo.py               # разбор транзакции, без базы
```

Нужны PostgreSQL с плагином wal2json (`apt install postgresql-16-wal2json`) и
python3. Без `ES_BIN` скрипт собирает бинарники сам (`go build`), как `scripts/demo.sh`.

## Что показал прогон

21.11.2026, бинарники релиза v0.5.0 (master отличается от него одной строкой
теста), PostgreSQL 16.15, wal2json 2.5, метки времени — встроенная демо-служба.
Каждая строка таблицы — проверка в `run.sh`: расхождение роняет скрипт.

| Что проверялось | Итог |
|---|---|
| До-образы доезжают до хранилища без правок в нём | да: строка wal2json — обычная запись источника |
| `subject_field: "xid"` собирает транзакцию в один пакет | да: 1175 записей транзакции открыты, 9 чужих в окне закрыты, `esverify` — VERIFIED |
| Отметка агента едет вместе с транзакцией | да: `pg_logical_emit_message` ложится в журнал под тем же xid |
| `application_name` сессии агента есть в журнале | нет, ни разу: чья транзакция, говорит только отметка |
| Откат возвращает базу к снимку до действия | да: 1171 обратный шаг; от снимка отличаются только строки, тронутые человеком |
| Строку, изменённую человеком после агента, откат не перезаписывает | да: конфликт показан (было / оставила транзакция / сейчас), строка не тронута |
| Строка изменилась между сверкой и откатом | откат не применён вовсе: транзакция отката сверяет число строк и отменяется целиком |
| Строка, тронутая транзакцией дважды; строка с полем в TOAST; удаление родителя после детей | возвращены верно |
| Повторный откат | применять нечего |
| Сам откат попадает в хранилище | да: своя транзакция с отметкой «кто, какую транзакцию, почему, какие конфликты оставил» |
| `TRUNCATE` | в журнале одна строка без данных; `undo.py` отказывает: до-образов нет |
| `DROP TABLE` | в журнале только начало и конец транзакции: ни имени таблицы, ни данных |
| Строка длиннее предела записи (1,5 МБ при пределе 1 МиБ) | сборщик режет её на две записи без метки; в пакет транзакции её до-образ не попадает |
| Ключ месяца уничтожен | пакет проходит проверку, тел нет, откат невозможен; журнал улик на диске — те же 3,5 МБ, что и до уничтожения |

Конфликт в выводе выглядит так:

```
шагов 1171: применить 1168, уже в нужном виде 1, конфликтов 2
  КОНФЛИКТ, шаг 505: public.orders (id=1) — под этим ключом снова есть строка
      транзакция удалила: account_id=«8», id=«1», item=«item 1», paid=«false»
      сейчас под ключом:  account_id=«8», id=«1», item=«re-entered by a human», paid=«false»
  КОНФЛИКТ, шаг 1170: public.accounts (id=6) — строку изменили после транзакции
      balance: было «1006.00», транзакция оставила «0.00», сейчас «777.00»
      note: было «it's a "vip" #6», транзакция оставила «closed by support-bot», сейчас «fixed by a human»
```

## Числа

Одно плохое действие агента: обнулить каждый третий счёт, удалить неоплаченные
заказы. Строки узкие (счёт — около 80 байт), одна машина, 2 ядра.

| Счетов в базе (`ROWS`) | 2 000 | 150 000 | 450 000 |
|---|---|---|---|
| Изменений строк в действии | 1 172 | 87 505 | 262 506 |
| Транзакция в самой базе | 0,02 с | 0,37 с | 0,74 с |
| Журнал wal2json | 0,7 МБ | 56 МБ | 169 МБ |
| Доставка до хранилища | 0,17 с | 13,9 с | 38,0 с |
| Хранилище: журнал улик и цепь | 1,1 МБ | 84 МБ | 253 МБ |
| Пакет по транзакции | 2,4 МБ | 180 МБ | не выдан |
| Выдача пакета и две проверки `esverify` | 0,25 с | 12,0 с | — |
| Сверка с базой | 0,09 с | 1,7 с | — |
| Применение отката | 0,05 с | 1,9 с | — |
| Место в хранилище к размеру обеих таблиц | 1,7 | 2,1 | — |

На изменение строки: 660–670 байт в журнале wal2json, 880–890 байт в журнале
улик и 114–115 байт в цепи. От конца окна до проверенного пакета — 139–147 с.
В третьем столбце объём хранилища — весь каталог данных на момент отказа.

## Что из этого следует

Хранилище идею держит: адресация по транзакции, проверяемость, «откат тоже
запись» получаются из того, что уже есть. Ограничения ниже — не догадки, каждое
вышло в прогоне.

1. **Откат не бывает раньше, чем через две минуты с лишним.** Пакет по субъекту
   закрывает метка времени, взятая больше чем через две минуты после конца окна,
   и ещё одна за ней (`docs/bundles.md`). Быстрее — только пакеты одной записи
   по номеру, а они не доказывают, что записи транзакции все.
2. **Место.** Около килобайта на изменённую строку при строке в 80 байт: одно
   действие заняло в хранилище в 1,7–2,1 раза больше, чем обе таблицы целиком. Уничтожение
   ключа делает тела нечитаемыми и ничего не освобождает. А без фильтра в журнал
   идут все транзакции над таблицами, не только агента: wal2json отбирает по
   таблицам, не по тому, кто писал.
3. **Темп.** База делает 262 тысячи изменений за 0,74 с, конвейер везёт их 38 с
   (6–7 тысяч записей в секунду на этой машине). Агент в цикле пишет быстрее,
   чем журнал уезжает из зоны поражения.
4. **Размер пакета.** Пакет несёт улики всех записей окна, а не одной
   транзакции: 180 МБ на 87 тысяч изменений. Транзакцию больше 250 000 записей
   один пакет не берёт (`the window spans 262546 leaves of the chain, more than
   250000 in one bundle`), а более короткие окна режут её посередине; склейку
   нескольких пакетов `undo.py` не умеет.
5. **Строка длиннее 1 МиБ пропадает из отката молча.** Её куски лежат в
   хранилище без метки. Заметить это можно только по счётчику `unlabeled` в отчёте
   `esverify -json`; `undo.py` при ненулевом счётчике отказывает, и отказ получает
   любая транзакция этого окна, потому что записи без метки ничьи.
6. **`TRUNCATE` и `DROP TABLE` не откатываются.** Когда агент не правит строки,
   а сносит таблицу или базу целиком, построчный журнал не спасает: нужна
   резервная копия. Про `DROP TABLE` журнал не говорит ничего.
7. **Связка с агентом — только через отметку в транзакции.** Ни роли, ни
   `application_name` в журнале нет. Отметку должен ставить компонент между
   агентом и базой; здесь его изображает функция `tx` в `run.sh`. Номер
   транзакции оператор тоже берёт у него.
8. **Настройка Postgres.** Таблицам нужен `REPLICA IDENTITY FULL`, иначе в
   старом образе только ключ (`undo.py` это замечает и отказывает). В сборке
   Ubuntu 16.15 плагин надо ещё разрешить: `output_plugin_libraries`.

## Чего опыт не проверял

- Сборку из исходников: в этой среде нет Go 1.25, прогон шёл на бинарниках
  релиза через `ES_BIN`.
- Настоящую службу меток времени, свидетелей и копию наружу.
- Остановку `pg_recvlogical`: слот тогда копит WAL на диске базы, а после сбоя
  транзакция приходит в файл повторно. Повтор `undo.py` разбирает (берёт
  последнюю целую пару B..C), но проверено это только на синтетическом вводе в
  `test_undo.py`.
- Типы без оператора равенства (`json`, `xml`), `bytea`, генерируемые колонки,
  последовательности. Триггеры таблиц при откате срабатывают как обычно.
- Нагрузку во время отката: проверена одна правка между сверкой и применением.
- Другие версии PostgreSQL и wal2json.

## Чего в опыте нет совсем

Детектора («массовое изменение», канарейки), выбора по каждому конфликту,
своего сборщика поверх протокола репликации, фильтра «только транзакции агента».

## Файлы

- `run.sh` — стенд и сценарий с проверками на каждом шаге.
- `undo.py` — `plan`: разбор транзакции в `plan.json` и `check.sql`; `sql`: по
  ответу базы пишет `undo.sql`. В базу сам не ходит, только stdlib.
- `test_undo.py` — 13 проверок разбора: порядок шагов, строка, тронутая дважды,
  смена ключа, повторная пересылка, отказы.
