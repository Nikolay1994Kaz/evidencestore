# Откат действия ИИ-агента в PostgreSQL по до-образам из хранилища

Ветка-опыт. Сначала здесь проверялось, ложится ли связка «аудит + откат» на
хранилище как оно есть (wal2json, запись на строку; итоги — в конце страницы).
Теперь в ветке первая реализация: свой сборщик на логической репликации и
MCP-сервер для агента. Код хранилища, `escollect` и `esverify` по-прежнему не
изменён ни строкой.

```
ИИ-агент
  → esmcp           MCP-сервер: запрос идёт ролью агента, в транзакции — отметка действия
  → PostgreSQL      права роли — то, что агенту можно; триггер пишет в журнал роль сессии
  → espgtap         читает журнал базы (pgoutput), берёт только транзакции агента и отката,
                    пишет сжатые части в journal.jsonl, поднимает тревоги
  → escollect       читает journal.jsonl как обычный журнал
  → evidencestore   источник с "subject_field": "xid"
  → esverify        записи транзакции, проверенные офлайн
  → undo.py         обратные операции, сверка с базой, одна транзакция отката
```

## Что где

| Часть | Что делает |
|---|---|
| `internal/pgwire` | клиент протокола PostgreSQL на stdlib: вход (trust, пароль, MD5, SCRAM-SHA-256), TLS, простые запросы, поток репликации |
| `internal/pgoutput` | разбор сообщений встроенного плагина `pgoutput` |
| `internal/pgtap`, `cmd/espgtap` | сборщик: отбор транзакций по отметке роли, поток транзакции в gzip, части до 700 КБ, индекс, тревоги; `-setup-sql` печатает настройку базы для DBA |
| `internal/mcpserver`, `cmd/esmcp` | MCP-сервер по stdio: `query`, `execute`, `actions`; отметка действия в транзакции, журнал квитанций |
| `undo.py`, `test_undo.py` | план отката из тел записей, `check.sql`, `undo.sql` |
| `mcp_call.py` | клиент MCP для сценария: вызывает инструмент так, как это делает агент |
| `run.sh` | стенд и сценарий с проверкой на каждом шаге |

## Запуск

```
experiments/pg-undo/run.sh              # десять секунд
WINDOW=1 experiments/pg-undo/run.sh     # ещё и пакет по окну времени: +2,5 минуты
ROWS=450000 experiments/pg-undo/run.sh  # 262 тысячи изменений в одном действии
python3 -I experiments/pg-undo/test_undo.py
go test ./internal/pgwire ./internal/pgoutput ./internal/pgtap ./internal/mcpserver
```

Нужны Go, PostgreSQL 14+ и python3. Плагин ставить не надо: `pgoutput` встроен.

## Как база узнаёт агента

В журнале PostgreSQL нет ни роли, ни `application_name`. Их кладёт туда сама
база (`espgtap -setup-sql`):

- у агента своя роль: `SELECT, INSERT, UPDATE, DELETE` на названные таблицы, без
  `TRUNCATE` и без владения. То, что по журналу не вернуть, агенту недоступно;
- на таблицах триггер на оператор: пишет в журнал роль сессии. Сообщение идёт
  перед изменениями своего оператора, поэтому сборщик уже к первому изменению
  знает, брать транзакцию или пропустить;
- отметку действия ставит MCP-сервер через `evidence.mark_action`. Напрямую
  звать `pg_logical_emit_message` роли агента нельзя: право отозвано;
- транзакция роли агента без отметки действия — тревога `no-action`: агент
  пришёл в базу в обход MCP-сервера. В журнал она попадает всё равно.

## Что проверяет сценарий

Прогон 21.11.2026, PostgreSQL 16.15. Каждая строка — проверка в `run.sh`.

| Что | Итог |
|---|---|
| Действие через MCP: запрос, отметка, квитанция | транзакция в журнале с ролью, сессией и номером действия; квитанция — в своём источнике хранилища |
| Агент просит `TRUNCATE`, `DROP TABLE`, снять триггер, подделать отметку | четыре отказа базы; квитанции с исходом `failed` |
| Агент пишет в базу мимо MCP | транзакция записана, тревога `no-action` |
| Плохое действие: 1173 изменения, среди них документ в 1,5 МБ | 2 записи хранилища; тревоги `mass-change` и `canary` |
| Правки человека (владельца таблиц) | в журнал до-образов не идут |
| До-образы из хранилища | пакеты записей, каждая VERIFIED, через 2,5 с после действия |
| Откат | база совпала со снимком; строки, тронутые человеком, не перезаписаны; документ вернулся |
| Строка изменилась между сверкой и откатом | откат не применён вовсе |
| Сам откат | своя транзакция в журнале: кто, какую транзакцию, почему, какие конфликты оставил |
| Пакет по окну времени (`WINDOW=1`) | VERIFIED; план из него совпал с планом из пакетов записей |

Отдельно проверено руками, вне сценария: вход по SCRAM-SHA-256 через TCP
(`PGWIRE_TEST_DSN=… go test ./internal/pgwire -run Live`); сборщик, убитый
`kill -9`, после запуска берёт транзакцию, прошедшую без него, и ничего не
дублирует.

## Числа: было и стало

Одно действие агента над 450 000 счетов: 262 507 изменений строк.

| | Опыт (wal2json, запись на строку) | Сейчас (espgtap) |
|---|---|---|
| Записей в хранилище | 262 509 | 10 |
| Журнал у сборщика | 169 МБ | 8,0 МБ |
| Место в хранилище | 253 МБ | 8,0 МБ |
| От фиксации до хранилища | 38 с | 2,3 с |
| Пакет с до-образами | не выдан: больше 250 000 листьев | 10 пакетов записей, 19 МБ, 0,7 с |
| Проверенные до-образы после действия | не раньше 139 с | через 5,3 с |
| Данные возвращены | — | через 33 с |
| Место к размеру таблиц | 2,1 | 0,06 |

На малом прогоне (2000 счетов, 1173 изменения) от действия до возврата данных
проходит 3 с. Из 1 МБ журнала там почти всё — один документ: полтора мегабайта
случайных шестнадцатеричных цифр сжимаются вдвое, строки таблиц — в десятки раз
(32 байта на изменение на большом прогоне). Данные стенда однообразны; на
настоящих сжатие будет хуже.

## Решения, которые разошлись с планом

1. **Ядро хранилища не тронуто.** Пакет по диапазону номеров не понадобился.
   Транзакция теперь занимает единицы записей, а пакет одной записи готов сразу
   после метки времени. Что части транзакции все, видно по ним самим: номера
   1..k, признак последней, счётчик изменений в итоге потока. Пакет по окну
   остаётся для аудита: он доказывает ещё и то, что других записей не было.
2. **Сборщик пишет файл, а не шлёт в хранилище сам.** Файл читает `escollect`
   со всеми его гарантиями (обещания, эпоха, пульс, свидетель голов), и его код
   не пришлось резать. Позицию базе сборщик подтверждает после `fsync` файла,
   а не после ответа хранилища: простой хранилища копит файл у сборщика, а не
   журнал у базы.

## Чего ещё нет

- Откат — скрипт `undo.py`: не на Go и не инструмент MCP. План строит и
  применяет человек.
- Номера записей транзакции берутся из индекса сборщика: строка журнала —
  запись источника. Это верно, пока журнал один файл и читается с начала;
  ротации журнала нет. Ошибку в номерах `undo.py` заметит по телам и откажет.
- Тревоги пишутся в файл и в журнал сборщика; наружу их никто не несёт.
- Слот, превысивший `max_slot_wal_keep_size`, база объявляет негодным: сборщик
  тогда не стартует, и пропуск в журнале сам не отмечается.
- DDL посреди транзакции, типы без оператора равенства (`json`, `xml`),
  генерируемые колонки, значения не в UTF-8: `undo.py` отказывает или не умеет.
  Первичный ключ сборщик читает из каталога в момент чтения журнала.
- `pgoutput` отдаёт транзакцию после фиксации: тревога о массовом изменении
  приходит, когда оно уже сделано.

## Чего не проверял

- MCP-сервер говорил только со своим клиентом (`mcp_call.py`, ревизия
  2026-07-28) и с тестами прежнего рукопожатия. С настоящим агентом — нет.
- TLS в `pgwire` (`sslmode=require`, `verify-full`), вход по MD5 и открытым
  паролем: код есть, живого прогона не было.
- Другие версии PostgreSQL, реплики и переключение на реплику, большие
  транзакции под нагрузкой (на стороне базы они декодируются с диска).
- Полный `go test ./...` шёл от root: три теста `internal/store`, которые
  закрывают каталог резерва через `chmod`, от root не проходят и на чистом
  master. От обычного пользователя на этой ветке они проходят.

## Что показал первый опыт (wal2json)

Его скрипт — в истории ветки (коммит 427d74a). Оттуда остаются в силе:

- `TRUNCATE` и `DROP TABLE` по журналу не вернуть. Теперь они закрыты агенту
  правами; владелец таблиц по-прежнему может, и это вне журнала.
- Таблицам нужен `REPLICA IDENTITY FULL`.
- Уничтожение ключа месяца делает до-образы нечитаемыми, а места не освобождает.
