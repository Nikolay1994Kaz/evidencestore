# Откат действия ИИ-агента в PostgreSQL по до-образам из хранилища

> **Устройство пересмотрено 23.11.2026 (DECISIONS, п. 42).** Третий заход
> эталона нашёл критичное в отметках «кто»: ключ отметок доставала роль с
> REPLICATION (FINDINGS, «эталон Postgres, заход 3»). Теперь «кто» берётся не
> из базы, а из подписанных квитанций шлюза (`receipt/v1`, п. 43): `esmcp` до
> COMMIT пишет намерение с номером транзакции, `esundo` — намерение отката, а
> база только наблюдается. Отметок, триггеров «кто», ключа в базе, RLS и
> режима по ролям больше нет; захват через pgoutput, отпечатки и пачки, откат
> с путём поиска из настроек и Docker остались. В master с v0.6.0 (до этого —
> ветка `pg-receipts`); обзор на английском — `docs/postgres.md`.

Сначала здесь проверялось, ложится ли связка «аудит + откат» на хранилище
как оно есть (wal2json, запись на строку; итоги — в конце страницы). Теперь
это реализация: сборщик читает журнал базы сам, для агента есть MCP-сервер,
откат — командой оператора и инструментом самого агента. Хранилище и
`esverify` добавили только квитанции шлюза (п. 43) и пакет по сделке
(`esverify -linked`); `escollect` стал универсальным — вход выбирается в
настройках.

```
ИИ-агент
  → esmcp           MCP-сервер, шлюз: запрос идёт своей ролью сервера; до COMMIT — подписанное
                    намерение с номером транзакции, после — исход (квитанции receipt/v1);
                    действие сверх предела строк откатывается до фиксации
  → PostgreSQL      роли решают, кто что может: пишет только роль сервера, своей ролью агент
                    только читает; своего в базе ничего — ни триггеров, ни отметок
  → escollect       источник "postgres": читает журнал базы (pgoutput), берёт все транзакции
                    по названным таблицам: названные в подписанном намерении шлюза — целиком,
                    остальные — отпечатком; сжатые части кладёт прямо в свой буфер;
                    тревоги несёт людям сам — в Telegram, Slack или на свой адрес;
                    тот же процесс читает и файлы квитанций шлюзов — свои источники receipt/v1
  → evidencestore   источник с "subject_field": "xid"
  → esverify        записи транзакции, проверенные офлайн
  → esundo          оператор: обратные операции, сверка с базой, одна транзакция отката
  → esmcp           агент: то же инструментами undo_preview и undo_apply (если включено)
```

## Сборщик один

Раньше базу читала отдельная программа (`espgtap`): она писала файл, а
`escollect` этот файл подбирал. Теперь `escollect` делится на две половины.
Доставка одна на все источники: номера записей, буфер на диске, обещания
хранилища, пульс, свидетель голов. Вход — откуда записи берутся: файл, файлы
по маске или журнал PostgreSQL. Новый вид источника — это новый вход
(`internal/input`), а не вторая программа.

Один процесс ведёт несколько источников. Общее — наверху, у каждого источника
свои сертификат, буфер и вход:

```json
{
  "server": "https://store:8443", "ca": "ca.crt", "store_key": "…",
  "sources": [
    {"cert": "pg-agent.crt", "key": "pg-agent.key", "spool_dir": "spool-pg-agent",
     "postgres": {
       "dsn": "host=db user=evidence_tap dbname=shop sslmode=verify-full",
       "dir": "pg-index",
       "mcp_roles": ["esmcp_bot"],
       "roles": ["agent_bot"],
       "undo_roles": ["undo_op"],
       "tables": ["public.accounts", "public.orders"],
       "receipts": {"files": ["mcp/receipts.jsonl", "undo/receipts.jsonl"],
                    "gateway_keys": ["<esmcp -pubkey>", "<esreceipt pubkey -key esundo.key>"],
                    "source": "pg-agent"},
       "alert_rows": 500}},
    {"cert": "agent-mcp.crt", "key": "agent-mcp.key", "spool_dir": "spool-agent-mcp",
     "file": "mcp/receipts.jsonl"},
    {"cert": "undo-op.crt", "key": "undo-op.key", "spool_dir": "spool-undo-op",
     "file": "undo/receipts.jsonl"}
  ]
}
```

Прежний вид настроек (один источник, без `sources`) работает как раньше.

Что это дало:

- Нет файла-посредника: записи не пишутся на диск дважды, и ротировать нечего.
  Доставленное буфер `escollect` удаляет сам.
- Номер записи известен точно: сборщик пишет в справочник (`index.jsonl`) те
  номера, под которыми сам шлёт транзакцию в хранилище.
- Обрыв связи с базой — не остановка: сборщик подключается снова, а
  накопленное тем временем доставляет.
- Потеря видна. Слот удалили или база стёрла журнал, который он не успел
  прочитать, — сборщик пропускает номер записи, и хранилище записывает в цепь
  пропуск.
- Позицию базе сборщик подтверждает после `fsync` своего буфера. Пока
  хранилище недоступно, копится буфер сборщика, а не журнал базы.

## Граница доверия

Всё, что обещано ниже, держится в этих границах. Что требует их нарушить, —
не ошибка, а предел; такие случаи названы в «Чего ещё нет».

- **Ключ шлюза агенту недоступен даже на чтение, а каталог квитанций, голову
  цепочки шлюза и состояние сборщика пишут только шлюз и сборщик.** Они идут
  своим пользователем, а не тем, под которым у агента есть shell (так в
  `deploy/docker`). Кто пишет в каталог квитанций без ключа, подделать
  квитанцию не может, но может вынуть строку и вернуть её, переписать файл,
  обойти счёт пределов до фиксации; многое из этого сборщик назовёт тревогой,
  но не всё.
- **Подъём базы из копии — событие, о котором люди знают.** Сборщик его видит
  (`db-rewound`) и снимает намерения прежней истории, но в редких сочетаниях
  подъёма с перезапуском базы чьей была транзакция сразу после подъёма, стоит
  проверить (ниже, «База ушла назад»).

## Что сборщик берёт и что обещает

Обещание — только то, что сборщик видит сам (DECISIONS, п. 41–42): **ни одна
транзакция по названным таблицам не пройдёт мимо хранилища, какой бы ролью
она ни шла, а чья она, говорит подписанная квитанция шлюза, не база.**
«Агент не может» держат роли базы (ниже, «Чья транзакция»), но это второй
рубеж: путей выдать права у PostgreSQL больше, чем может перечислить любая
проверка.

- **Транзакция, названная в подписанном намерении шлюза**, — целиком: строки
  «до» и «после», её можно откатить. Намерение — квитанция `receipt/v1` шагом
  `intent` (`esmcp`) или `undo` (`esundo`) со ссылкой `{"source": "<источник
  базы>", "subject": "<xid>"}`. Шлюз пишет его до COMMIT, а поток отдаёт
  транзакцию после, поэтому сборщик решает на её Begin. Подпись — ключом
  шлюза из `receipts.gateway_keys`: ключ лежит у шлюза, в базе его нет, и ни
  журнал, ни копия базы, ни роль с REPLICATION его не несут.
- **Всё остальное** — люди, приложения, роль, которой кто-то вошёл мимо шлюза,
  — **отпечатком**: xid, время фиксации, таблицы, ключи строк, вид изменения
  и хеши старой и новой строки (первые 16 байт SHA-256). Чья транзакция,
  отпечаток не говорит: роли в журнале нет, а из базы она больше не берётся.
  Самих строк нет: откатить такую транзакцию из хранилища нельзя, `esundo`
  отказывает и называет запись, где лежит отпечаток. Строки — из бэкапа, а
  хеш говорит, та ли это строка (рецепт — ниже). С `"require_gateway": true`
  каждая такая транзакция — тревога `not-via-gateway`: для базы, где пишет
  только шлюз.
- Сообщения журнала (`pg_logical_emit_message`, outbox приложения) ничего не
  решают: сборщик их и не просит. Строка файла квитанций, подписанная не
  ключом шлюза, — тревога `forged-receipt`, и она тоже ничего не решает.
  Намерение старше фиксации больше чем на сутки — не о ней: xid 32 бита и
  занимается снова. Номер сверяется ещё и с эпохой (`xid8` в теле намерения:
  esmcp и esundo его пишут), и намерение решает одну транзакцию: какое
  намерение какую транзакцию решило, лежит в `receipts-spent.jsonl` рядом со
  справочником. В памяти — 200 000 последних намерений.
- **Поток — всегда от места слота**, а не от места сборщика. Ниже своего
  места сборщик узнаёт повтор того, что уже лежит в буфере, по справочнику:
  на том же месте журнала — та же транзакция (номер и время фиксации). Повтор
  не пишется второй раз; другая транзакция там — новая, и она пишется. Сверка
  — по 262 144 последним транзакциям буфера (в памяти, при подключении — из
  справочника с конца); ниже них повтор — по месту, как раньше.
- **База ушла назад** — поднята из копии или её место заняла отставшая
  реплика. Видно при подключении: конец её журнала ниже места сборщика, другая
  линия времени, другой кластер (`IDENTIFY_SYSTEM`) или следующий номер
  транзакции не выше прочитанного (`xid8`). И в потоке: ниже места сборщика —
  транзакция, которой у него там нет (журнал поднятой базы успел уйти за его
  место, пока его не было). Тогда тревога `db-rewound`, и намерения шлюза до
  неё не в счёт: их номера база выдаст снова другим транзакциям. esmcp и
  esundo кладут в намерение запуск базы из транзакции действия
  (`db_started`): намерение не в счёт, если его база запущена не позже
  последней транзакции прежней истории, прочитанной сборщиком, — в часах
  самой базы, и перезапуск поднятой базы до подключения сборщика её действий
  не снимает. Намерения без этой отметки (другие шлюзы) — не в счёт все
  прочитанные до подъёма. Подъём узнаётся по месту сборщика и по запуску
  базы: та же копия, поднятая снова, — снова тревога, и не в счёт всё, что
  писалось не в нынешнем запуске. Реплика, запущенная раньше и занявшая
  место, — действия между переключением и подключением сборщика ложатся
  отпечатком.
- **Слот сдвинули**, пока сборщик не был подключён (роль с REPLICATION,
  `pg_replication_slot_advance`, или слот пересоздали): каждая позиция
  пишется в `slot.json` (с fsync каталога) до того, как сборщик подтвердит её
  серверу, и слот дальше записанного и дальше места сборщика — пропуск в
  номерах и тревога `gap`. Сдвинутый слот читается дальше от своего места;
  пересоздаётся только слот, чей журнал база стёрла. `slot.json` пропал —
  тревога `slot-unknown`: сдвинут ли слот, не сказать; испорчен — сборщик не
  запускается.
- **Файл квитанций** читается кусками; строка длиннее любой квитанции
  пропускается; строки без подписи ключом шлюза — одна тревога на чтение.
  Файл ротировали или заменили — старый дочитывается, дальше новый (ушедший,
  пока сборщик стоял, находится в том же каталоге по inode). Файл не прочесть
  (на его месте каталог, FIFO, нет прав) — тревога `receipts-unreadable`, а
  вход идёт дальше: транзакции шлюза — отпечатком, пока файл не прочтётся.
  Исход обработан, если хэш его квитанции — в `receipts-alerted.jsonl`, а не
  по месту в файле: ни обрезка, ни сдвиг содержимого, пока сборщик стоял, ни
  копия прежней строки, ни вторая цепочка с тем же именем шлюза не поднимают
  старых тревог и не глушат новых. Файл квитанций открывается только сам —
  ссылка на месте пути не принимается — и только обычный; дыры разреженного
  файла не читаются.
- **Строка вынута из файла.** Цепочку шлюза сборщик помнит по каждому файлу
  (и после перезапуска): квитанции нет между двумя прочитанными — тревога
  `receipts-gap`; исход с номером транзакции, чьего намерения сборщик не
  читал, — `intent-missing`, транзакция легла отпечатком; так же — намерение,
  пришедшее после того, как сборщик прочёл его транзакцию. Так видно, если
  писатель файла без ключа вынул намерение, пока шло действие (и вернул ли
  он его потом на место), или файл повернули и сжали, пока сборщик стоял.
- **Обновление** с установки на отметках: остановить старый esmcp (и откаты),
  дать старому сборщику дочитать слот, остановить его, выполнить новый
  `escollect -setup-sql`, запустить новый сборщик с разделом `receipts` и
  новый esmcp с ключом шлюза. Действие старым esmcp после остановки старого
  сборщика ляжет отпечатком: намерения у него нет. Файлы квитанций — новые
  (другой путь): строки старого журнала квитанциями `receipt/v1` не
  подписаны, и по тому же пути сборщик назовёт их тревогой `forged-receipt`.
  Скрипт снимает то, чем владеет `evidence_owner` (функции, ключ, схему
  `evidence`, триггеры `evidence_who`), и саму роль, когда на неё не
  ссылается ни одна база сервера (стояла в нескольких — скрипт в каждой);
  схема `evidence`, где есть объекты других ролей, остаётся у владельца базы.
  Право писать сообщения журнала возвращается `PUBLIC`, как было до него.
- Отпечатки складываются **пачкой**: одна запись хранилища на 500 транзакций,
  не больше части (700 КБ сжатого), и пачка не старше минуты (у `-once` — до
  конца прохода). Отпечаток крупнее 256 КБ (около 3000 строк) пишется своими
  записями, как полная транзакция: ни запись, ни память сборщика от размера
  транзакции не зависят. Пока она не ушла,
  место в журнале базе не подтверждается: упадёт сборщик — база пришлёт
  транзакции снова.
- Тревоги у отпечатков — как у полных транзакций: ловушка, массовое
  изменение, `TRUNCATE`, и `not-via-gateway` с `require_gateway`. Без команды
  отката: откатить отпечаток нельзя.
- Раздела `receipts` нет — шлюза нет: каждая транзакция целиком, и чья она,
  записи не говорят.

Объём (замер 23.11 на стенде `run.sh`, хранилище плюс справочник сборщика):

| Транзакция | Целиком | Отпечатком |
|---|---|---|
| одна строка счёта | ~1,2 КБ | ~0,2 КБ (хранилище ~0,1 КБ) |
| десять строк счёта | ~1,6 КБ | ~0,7 КБ |
| документ в 1 КБ (случайный текст) | ~2,1 КБ | ~0,18 КБ |
| все 2000 счетов одной транзакцией | 44 Б на изменение | 53 Б на изменение |
| одна строка раз в 12 с | ~1,2 КБ | ~0,37 КБ |

Узкие похожие строки целиком сжимаются лучше случайных хешей, поэтому в
массовом изменении отпечаток дороже. На широких и разных строках он дешевле в
разы. Правка, которая за минуту оказалась в пачке одна, стоит около 0,96 КБ:
почти всё — цена самой записи хранилища.

**Хеш строки** — первые 16 байт SHA-256 в base64 без `=`, от колонок строки
подряд, в порядке таблицы: NULL — `-`, значение — длина его текста в байтах
UTF-8, `:` и текст. Текст — функцией вывода типа (`format('%s', …)`, не
`::text`: у `bool`, `char(n)`, `inet` они разные), с настройками, которые
сборщик ставит своему сеансу, что бы ни стояло у сервера, базы и роли.
Колонки — те, что пишет журнал: до PostgreSQL 18 — без генерируемых.
Пересчитать по бэкапу:

```sql
SET TimeZone = 'UTC'; SET DateStyle = 'ISO, YMD'; SET IntervalStyle = 'postgres';
SET extra_float_digits = 3; SET bytea_output = 'hex'; SET search_path = pg_catalog, pg_temp;
SELECT id, rtrim(encode(substr(sha256(convert_to(concat(
         CASE WHEN id IS NULL THEN '-' ELSE octet_length(convert_to(format('%s', id), 'UTF8')) || ':' || format('%s', id) END,
         CASE WHEN note IS NULL THEN '-' ELSE octet_length(convert_to(format('%s', note), 'UTF8')) || ':' || format('%s', note) END
         -- … каждая колонка журнала по порядку
       ), 'UTF8')), 1, 16), 'base64'), '=')
FROM public.accounts WHERE id = 6;
```

У таблицы без REPLICA IDENTITY FULL хеша старой строки нет, а новой — если
значение в TOAST не менялось и в журнал не пришло (тогда `partial`).

**Чего вход не обещает:**

- DDL в журнал базы не идёт. Видно только то, что ловит проверка владения и
  CREATE в `-setup-sql`, и тревога `identity` о новой секции.
- Суперпользователь базы и тот, кто читает секреты ОС (пароли ролей из
  `mcp.json` и `undo.json`, ключи шлюзов), — вне модели: суперпользователь
  выключит слот, а с ключом шлюза намерения пишутся от его имени.
- Таблицы вне `tables` — вне.
- Остановить до фиксации можно только через MCP-сервер (пределы строк,
  частоты, таймауты). Всё остальное видно после фиксации.
- Хеш строки с малым разнообразием значений (флаг, статус) подбирается
  перебором. Тела записей в хранилище зашифрованы, но тот, кому выдали пакет,
  хеши видит.

## Тревоги

Раньше тревога была строкой в файле, и человек её не видел. Теперь сборщик
несёт её сам. Раздел `notify` в настройках источника `postgres`:

```json
"down_after": "1m",
"notify": {
  "undo_hint": "esundo check -config /etc/evidence/undo.json -xid {xid}",
  "to": [
    {"type": "telegram", "token": "123456:ABC…", "chat": "-1001234567890"},
    {"type": "slack", "url": "https://hooks.slack.com/services/T…/B…/…"},
    {"type": "json", "url": "https://alerts.example.com/hook"}
  ]
}
```

`telegram` — бот: ключ от @BotFather и номер чата (или `@канал`), бот должен
состоять в чате. `slack` — входящий веб-хук Slack и совместимые с ним
(например, Mattermost): уходит `{"text": …}`. `json` — свой адрес: уходит
`{"text": …, "title": …, "events": […]}`.

Сообщение на транзакцию одно — со всеми поводами, сводкой и командой отката:

```
evidencestore, database shop: agent transaction 749
• canary: public.accounts: the canary row id=3 was touched (U)
• mass-change: 1173 row changes in one transaction (the threshold is 500)
action: 20261121T154707Z-1dd00158ac08, agent support-bot (receipt 21 of gateway esmcp) — reason given: "close inactive accounts"
changed: 1173 rows — public.accounts (updated 667, deleted 1); public.orders (inserted 1, deleted 503); public.docs (updated 1)
store records: 3–4
undo preview: esundo check -config /etc/evidence/undo.json -xid 749
```

Поводы:

| Повод | Когда |
|---|---|
| `mass-change` | изменений в транзакции не меньше `alert_rows` |
| `canary` | тронута строка-ловушка из `canaries` |
| `not-via-gateway` | с `require_gateway`: транзакция без намерения шлюза — в базу, где пишет только он, писали в обход |
| `forged-receipt` | строки файла квитанций не подписаны ключом шлюза: их дописал тот, у кого ключа нет, или шлюз умер посреди строки; одна тревога на чтение файла |
| `receipts-gap`, `intent-missing` | в файле квитанций нет квитанции цепочки шлюза между двумя прочитанными; исход действия с номером транзакции без прочитанного намерения или намерение, пришедшее после своей транзакции, — транзакция легла отпечатком |
| `receipts-unreadable` | файл квитанций не прочесть (каталог, FIFO, права): транзакции шлюза — отпечатком, пока не прочтётся; и когда прочёлся снова |
| `truncate`, `identity` | по записи эту транзакцию целиком не вернуть |
| `refused` | MCP-сервер остановил действие: строки, частота или время (см. ниже); по квитанции исхода |
| `escaped` | SQL агента сам закрыл транзакцию MCP-сервера: что он изменил, могло зафиксироваться мимо пределов. С `PREPARE` (ниже) до этого не дойти; тревога — страховка |
| `db-down`, `db-up` | связи с базой нет дольше `down_after`; связь вернулась |
| `slot-lag`, `slot-ok` | база копит журнал для слота: половина предела и 80 %; журнал отпущен |
| `gap` | записи потеряны: слот удалён или пересоздан, сдвинут кем-то, пока сборщик не был подключён, или база стёрла его журнал |
| `slot-unknown` | `slot.json` сборщика пропал: сдвинут ли слот, пока сборщика не было, не сказать |
| `db-rewound` | база ушла назад: поднята из копии, её место заняла реплика (другая линия времени), это другой кластер, или ниже места сборщика пришла транзакция, которой у него нет; намерения шлюза до неё не в счёт |

Как устроена доставка:

- Файл `alerts.jsonl` остаётся, но как очередь. Тревога сначала ложится в него
  с `fsync`, потом отправляется. Получатель недоступен — она ждёт и уходит
  позже. Сбор записей отправку не ждёт.
- У каждого получателя своя очередь: недоступный Telegram не держит Slack.
- После долгого простоя получателя старые тревоги уходят одной сводкой,
  последние десять — по одной.
- Доставка «хотя бы один раз»: после падения сборщика сообщение может прийти
  дважды, но не потеряться.
- Адреса получателей — секреты (в адресе сидит ключ): в журнал сборщика они
  не попадают, в том числе в тексте ошибок. Адрес — только `https://`;
  `http://` принимается для этой же машины.

## Пределы для агента

База отдаёт транзакцию сборщику после фиксации, поэтому тревога о массовом
изменении всегда значит «уже случилось». MCP-сервер стоит раньше фиксации, и
пределы — в его настройках. Всё держится на одном: транзакцию ведёт сервер,
и до его `COMMIT` ничего не зафиксировано.

**Транзакцию ведёт сервер.** Агент даёт команды: одну в `sql` или несколько в
`statements` (до 100, по порядку, одной транзакцией). Каждая идёт в базу
обёрнутой в `PREPARE` и расширенным протоколом: разбор допускает в тексте
одну команду, а грамматика `PREPARE` — только `SELECT`, `INSERT`, `UPDATE`,
`DELETE`, `MERGE` и `VALUES`. `BEGIN`, `COMMIT`, `ROLLBACK`, `SET`, `DO`,
`CALL` и изменения схемы база отвергает при разборе; все `PREPARE` действия
идут раньше всех `EXECUTE`, поэтому не исполняется ни одна его команда.
Список разрешённого проверяет грамматика самой базы, а не разбор текста в
сервере. До 22.11 текст шёл простым протоколом: `BEGIN; DELETE …; COMMIT;`
при пределе 1 строка удалял всё, а агент и люди слышали «nothing changed»
(P-239 в `docs/dev/FINDINGS.md`). Каждый вызов начинается с `DISCARD ALL`:
что SQL агента сменил на весь сеанс (`set_config(…, false)`,
рекомендательные замки), следующий вызов уже не видит.

Свои запросы сервер шлёт со своими настройками, а не с теми, что оставил SQL
агента: после его команд в той же пачке идут `SET LOCAL search_path =
pg_catalog, pg_temp`, `client_encoding = 'UTF8'` и `ROLE NONE`; отказ — в
квитанции исхода, а не в журнале базы. Литералы клиент пишет так, что база
читает их одинаково при любом `standard_conforming_strings` (`E'…'` у строки
с чертой). До 22.11 агент ставил свою схему раньше `pg_catalog`, и счёт строк
звал его функции (0 строк — действие сверх предела проходило); смена
`client_encoding` в действии ломала отметку об отказе, и тревоги не было; а
при `standard_conforming_strings = off` у базы или роли значение строки,
которое записал агент, исполнялось как SQL в сеансе `esundo` у человека
(P-242, P-243, P-256). Отложенные
ограничения и триггеры (`DEFERRABLE INITIALLY DEFERRED`) сервер срабатывает
до счёта (`SET CONSTRAINTS ALL IMMEDIATE`): раньше они шли на `COMMIT`, уже
после проверки предела (P-246). Если связь оборвалась на самом `COMMIT`,
агент слышит «исход неизвестен, не повторяй», а не «откатилось» (P-250).

```json
"action_row_limit": 500,
"window_rows": 5000, "window": "10m",
"actions_per_minute": 30,
"statement_timeout": "1m",
"lock_timeout": "10s"
```

| Предел | Что останавливает | Что происходит |
|---|---|---|
| `action_row_limit` | одно действие меняет слишком много строк | откат до фиксации |
| `window_rows` за `window` | агент дробит большое изменение на части | откат до фиксации той части, что переполнила окно |
| `actions_per_minute` | агент в цикле | отказ раньше, чем действие пойдёт в базу |
| `statement_timeout` | запрос висит или ждёт блокировку | запрос отменяется на сервере базы, соединение закрывается |

В каждом случае агент получает отказ со словами «не дроби и не повторяй,
позови человека», в квитанциях остаётся исход и причина, а сборщик по
квитанции исхода поднимает тревогу `refused`: люди узнают о том, чего в базе
не случилось. Агент в цикле
людей не заваливает: тревога о частоте — не чаще раза в минуту, а в квитанциях
— каждый отказ.

Как это устроено и почему так:

- **Строки считает сама база** (статистика текущей транзакции), а не разбор
  ответов: в счёт входят изменения внутри `WITH`, триггерами и каскадом. Не
  сосчитать — не фиксировать. Счёт — разность до и после SQL агента:
  статистика сеанса держит и прошлые транзакции, пока база их не сбросит (не
  чаще раза в секунду), и до 22.11 действие вслед за другим получало его
  строки к своим (P-240).
- **Счёт за время — по файлу квитанций**, общему для всех сеансов агента.
  Счёт в памяти сервера обнулялся бы с каждым новым сеансом. Проверка, само
  действие и квитанция идут под замком агента (`flock` на файле рядом с
  квитанциями): до 22.11 при пределе 4 в минуту из 30 одновременных сеансов
  проходило до 30 (P-252). Замок занят дольше, чем может идти одно действие,
  — отказ с объяснением.
- **Откат через MCP — тоже действие:** под теми же пределами, в счёт частоты,
  и только своих действий того же агента и той транзакции, которую сборщик
  взял по намерению этого действия. Строки отката перед фиксацией считает статистика его
  транзакции — с тем, что изменили триггеры и каскады. Откат отката не
  берётся: им агент повторял бы то, что откатили (P-247, P-249, P-264).
- **Соединение сервера входит со своими параметрами:** `role = none`, свои
  таймауты. Параметры входа сильнее умолчаний роли, и `DISCARD ALL` возвращает
  к ним. До захода 2 агент ставил умолчания роли, которой ходил и сервер
  (`ALTER ROLE … SET`), и `statement_timeout = 1` гасило все тревоги вне
  транзакции (P-259). Теперь у сервера своя роль (раздел «Чья транзакция»), а
  параметры входа — второй рубеж. Время
  квитанции ставится после замка агента (P-261), причина — не длиннее 2000
  байт.
- **Таймер — в MCP-сервере, а не только в базе.** `statement_timeout` роли —
  значение по умолчанию: `SET` агенту не дают, но `SELECT set_config(…)` —
  обычный `SELECT`, и таймаут базы агент себе снимет. Таймер сервера агенту
  недоступен. Таймауты роли
  (`escollect -setup-sql` ставит `statement_timeout`, `lock_timeout` и
  `idle_in_transaction_session_timeout`) остаются вторым рубежом — для
  сеансов роли агента, которыми он только читает.
- `statement_timeout` и `lock_timeout` заданы по умолчанию (минута и десять
  секунд); `"0s"` — без предела. Остальные пределы по умолчанию выключены.

## Отставание слота и показатели сборщика

Слот теряется не вдруг: сначала база копит для него журнал. Сборщик раз в
десять секунд спрашивает у базы, сколько журнала она держит для слота, и
поднимает тревогу `slot-lag` на половине предела базы
(`max_slot_wal_keep_size`) и снова на 80 %, а `slot-ok` — когда журнал отпущен.
Причина бывает и при исправном сборщике: долгая открытая транзакция в базе не
даёт слоту отпустить журнал. Если предел в базе не задан или велик, свой порог
задаёт `"slot_alert_mb"` в разделе `postgres`.

Те же числа и остальное — на странице для Prometheus. В настройках сборщика,
наверху:

```json
"metrics_listen": "127.0.0.1:9465"
```

| Показатель | Что значит |
|---|---|
| `escollect_spool_pending_records` | записей в буфере, которые хранилище ещё не приняло |
| `escollect_store_last_contact_timestamp_seconds` | когда хранилище последний раз ответило |
| `escollect_loop_timestamp_seconds` | когда цикл сборщика последний раз прошёл; перестал расти — цикл завис |
| `escollect_postgres_connected` | поток из базы открыт |
| `escollect_postgres_slot_retained_bytes`, `…_limit_bytes`, `…_safe_bytes` | сколько журнала база держит для слота, предел и запас |
| `escollect_postgres_slot_lag_bytes` | на сколько подтверждённая позиция отстаёт от конца журнала |
| `escollect_alerts_waiting`, `escollect_alerts_target_failing` | тревоги в очереди получателя; получатель отказывает |

У каждого значения метка `source`; процесс с несколькими источниками отдаёт
одну страницу на всех. Чего показатели не скажут: упавший сборщик страницу не
отдаёт. О нём говорит хранилище (источник замолчал) и сам Prometheus.

## От тревоги до отката — две команды

`esundo` теперь сам достаёт записи транзакции из хранилища и проверяет их.
Настройки оператора, `undo.json`:

```json
{
  "dsn": "host=db user=undo_op dbname=shop sslmode=verify-full",
  "index": "/var/lib/escollect/pg-index/index.jsonl",
  "stamp": ["evidencestore", "stamp", "-config", "/etc/evidencestore.json"],
  "proof": ["evidencestore", "proof", "-config", "/etc/evidencestore.json", "-source", "pg-agent", "-dek"],
  "verify": ["esverify", "-store-key", "…", "-tsa-trust", "/etc/evidence/tsa-root.crt"],
  "receipts": "/var/lib/esundo/receipts.jsonl",
  "key": "/etc/evidence/esundo.key",
  "pg_source": "pg-agent"
}
```

Голову цепочки своих квитанций шлюз (esundo, esmcp, `esreceipt sign`) держит
рядом с ключом (`"head"`, по умолчанию `<ключ>.head-<8 hex>`), а не рядом с
файлом квитанций: её пишет только шлюз, и писатель файла без ключа цепочку не
раздвоит (docs/receipts.md). Писать туда шлюз должен уметь, а каталог
квитанций — не её место: esmcp при запуске, `esundo apply` до базы и
`esreceipt sign` это проверяют и иначе не идут дальше — каталог ключа только
для чтения или ключ рядом с квитанциями, задайте `"head"`. В Docker каталог
ключа esmcp смонтирован только для чтения, голова — в `./state/mcp-head`
(init каждый раз чинит его владельца и права).

```
esundo check -config undo.json -xid 749                       # команда из тревоги: план и сверка с базой
esundo apply -config undo.json -plan undo-749.json -by nikolay  # применить
```

`esundo apply` до изменений отката пишет его намерение в свой файл квитанций
(ключ — `esreceipt keygen`, его открытый ключ — в `receipts.gateway_keys`
сборщика и `gateway_key` источника у хранилища): по нему сборщик берёт откат
целиком, и откат тоже можно проверить и откатить.

Вторую команду `esundo check` печатает сам. Тот же раздел настроек — у
MCP-сервера (`undo`), если откат разрешён и агенту.

| `run.sh` | стенд и сценарий с проверкой на каждом шаге |

## Docker

`compose.yaml` в корне — проба на одной машине: PostgreSQL 17 с
`wal_level=logical` и демонстрационными таблицами, хранилище, сборщик и
MCP-сервер.

```sh
docker compose up -d                       # при первом запуске — сертификаты, ключ, пароли в ./state
docker compose run --rm -T --no-deps esmcp # MCP-сервер для агента (stdio): эту команду даёт клиенту MCP
docker compose exec store esundo check -config /state/store/undo.json -xid N
docker compose exec store esundo apply -config /state/store/undo.json -plan undo-N.json -by ИМЯ
```

- Первый запуск (`init`, `deploy/docker/init.sh`) делает всё, что в
  `run.sh` руками: демонстрационный УЦ и сертификаты, `evidencestore init`,
  настройки всех программ, случайные пароли ролей, SQL `escollect -setup-sql`.
  Второй запуск ничего не трогает. Каждому контейнеру — только свой каталог
  `./state`: хранилищу — ключи и данные, сборщику — сертификаты источников и
  пароль своей роли, MCP-серверу — пароль роли сервера и ключ шлюза `esmcp`,
  хранилищу — ещё и ключ `esundo` (откат делают там). Квитанции откатов —
  в `./state/undo-receipts`.
- `db-setup` применяет SQL настройки базы при каждом `up`: он повторяем.
- Откат делает оператор — `esundo` в контейнере хранилища: пакеты записей ему
  выдаёт само хранилище. У агента инструментов отката здесь нет: им нужны
  команды хранилища из контейнера MCP-сервера.
- Тревоги — в `./state/pg-index/alerts.jsonl` и в журнале сборщика
  (`docker compose logs collector`). Людям — раздел `notify` в
  `./state/collector/collector.json`.
- `./state/agent.txt` — подключение для агента напрямую, только чтение.
- Файлы `./state` принадлежат пользователю программ в контейнерах (uid
  10001) и закрыты для остальных: с хоста их читают через `sudo` — или
  пользователь хоста с тем же uid (`getent passwd 10001`). Пароль
  суперпользователя базы — не в `./state`, а в томе `dbsecret`.
- `init` при каждом `up` пишет SQL настройки базы заново, той версией, что в
  образе, и `db-setup` его применяет: после обновления образа права ролей в
  базе — той же версии, что сборщик.
- Другая версия базы: `PG_VERSION=14 … 18`, с начала (`docker compose down -v
  && rm -rf ./state`).
- Это проба: УЦ демонстрационный, метки времени — от встроенной службы
  хранилища, всё на одной машине. Настоящая установка — `docs/install.md`.

Проверено без Docker: реестр образов из этой среды недоступен. Скрипт первого
запуска, настройки, SCRAM-вход ролей по паролям, `db-setup` дважды, хранилище
и сборщик под пользователем 10001, действие через MCP, отпечаток правки
человека, откат `esundo` по `undo.json` и остановка хранилища по `TERM`

## Откат на настоящей схеме

Стенд — три таблицы без связей. На открытых базах (Pagila, «Авиаперевозки»
Postgres Pro) откат поначалу отказывал; что изменено и почему — FINDINGS,
P-232…P-238, и DECISIONS, п. 37. Коротко:

- **Каскады внешних ключей.** Шаги идут в порядке, обратном журналу. Если
  база на нём отказывает по ограничению (детей удалил или переписал каскад:
  в журнале они стоят после родителя), `esundo apply` сам пробует второй
  порядок, по внешним ключам из каталога, и говорит об этом.
- **Триггеры при откате работают.** Откат — обычная транзакция владельца.
  Триггер, который переписывает строку при правке (`last_update = now()`),
  перепишет и то, что вернул откат. После отката строки сверяются с
  до-образами в той же транзакции, и `esundo apply` называет таблицу, колонку
  и число строк, где значения не те, что были. Pagila, PostgreSQL 17.12: агент
  сменил номера трём категориям, каскад переписал 190 строк `film_category`:

  ```
  undo applied: 193 steps in transaction 1076
    the steps went in the order of the foreign keys: in the order of the journal the database refused them (a cascade made a part of the changes)
    checked after the undo: the rows are back, but not all values are as they were before the transaction.
    Triggers of these tables rewrote what the undo put back (the undo does not switch triggers off):
      public.category.last_update: 3 rows
      public.film_category.last_update: 190 rows
  ```

  У `undo_apply` то же — в поле `differs_from_before`.
- **Чужие ссылки на вставленную строку.** Агент вставил строку, а потом на
  неё сослались строки, которых откат не касается, и ключ у них с `ON DELETE
  CASCADE` или `SET NULL`. Убрать строку значило бы молча удалить их или
  обнулить им ссылку. Сверка называет такой шаг конфликтом и говорит, кто
  ссылается; `esundo apply` перед уборкой проверяет то же ещё раз, под замком.
- **Секционированная таблица.** В `tables` называют её саму: скрипт
  `-setup-sql` настраивает и каждую секцию.
- **Типы без оператора равенства** (`point`, `json`, `xml`) сверяются текстом.
- **Генерируемые колонки** откат не пишет: их считает база. Правка возвращает
  только колонки, которые транзакция меняла, поэтому работает и таблица с
  `GENERATED ALWAYS AS IDENTITY`; удалённая строка возвращается со своим
  прежним номером.

## Чья транзакция

В журнале PostgreSQL нет ни роли, ни `application_name`, и «кто» из базы
больше не берётся (DECISIONS, п. 42): его говорит подписанная квитанция шлюза.
Что кому можно, решают роли базы (`escollect -setup-sql`):

- **чья транзакция, решает намерение шлюза.** `esmcp` пишет его с номером
  транзакции до SQL агента и тем более до COMMIT: не записалось — действия
  нет. `esundo` — так же для отката. Ключ шлюза — в его файле (права 600),
  агенту недоступен, как и пароль роли сервера. Транзакция роли сервера без
  намерения (её пароль украли, ею вошли мимо сервера) — отпечаток, с
  `require_gateway` — тревога `not-via-gateway`; какой ролью она шла,
  отпечаток не скажет;
- **граница между агентом и сервером — роли базы** (DECISIONS, п. 39). Три
  роли:
  - `mcp_roles` — роли MCP-серверов: `SELECT, INSERT, UPDATE, DELETE` на
    названные таблицы. Без `TRUNCATE` и без владения: то, что по журналу не
    вернуть, недоступно и SQL агента;
  - `roles` — роли агентов для прямого доступа: только `SELECT`. Запись,
    выданную этим ролям раньше (до п. 39 агент и сервер ходили одной ролью),
    скрипт отзывает;
  - `undo_roles` — роли, которыми откатывает `esundo`: запись в таблицы. Не
    суперпользователь и не владелец таблиц. Её транзакции берутся целиком по
    намерению `esundo`;
- **роли агента и сервера проверяются разрешённым перечнем.** Всё, что им
  можно, выдаёт скрипт, им самим. `-setup-sql` отказывает, если такая роль
  состоит в какой-либо роли (группа с правом на запись, `pg_signal_backend`,
  `pg_read_server_files`, роль-владелец схемы — через членство приходят права,
  которых скрипт не знает) или чем-либо владеет в базе (схемой, функцией,
  самой базой: владелец удаляет своё мимо журнала и возвращает себе права).
  Ролью сервера не может стать никакая другая роль со входом, кроме
  суперпользователей;
- **SQL агента идёт ролью сервера,** поэтому роли агента и сервера — ни сами,
  ни через `PUBLIC` — не обрывают и не отменяют сеансы, не берут того, что
  `initdb` или расширение оставили
  суперпользователям (`pg_read_file`, `dblink_connect_u`, колонка
  `pg_authid.rolpassword`…), не зовут чужих функций `SECURITY DEFINER` (кроме
  функций триггеров), не пользуются сторонними серверами (`dblink`,
  `postgres_fdw`: сопоставление `FOR PUBLIC` даёт SQL ролью владельца — мимо
  сборщика) и не меняют параметров уровня суперпользователя (`track_counts =
  off` — и счёт строк молчит). Функции `SECURITY DEFINER` приложения по
  умолчанию открыты `PUBLIC`: такие скрипт отказывает, им нужен `REVOKE EXECUTE
  … FROM PUBLIC` и выдача ролям, которым они нужны. Скрипт отзывает
  у `PUBLIC` `pg_terminate_backend` и `pg_cancel_backend` и выдаёт их
  `pg_signal_backend`: сеансы своей роли PostgreSQL даёт обрывать всегда, и так
  SQL агента обрывал сеанс сервера посреди действия (P-275). Обычные роли базы
  своих сеансов этими функциями больше не прервут; отмена запроса протоколом
  (Ctrl-C в `psql`) работает. Приложения, которые обрывают свои сеансы,
  получают EXECUTE отдельно — своей роли (`GRANT EXECUTE … TO <роль>`), не
  `PUBLIC` и не ролям агента и сервера: с правом у `PUBLIC` `esmcp` не
  работает. Сообщения журнала (`pg_logical_emit_message`, outbox) — не в
  счёт: из журнала «кто» не берётся;
- роль агента не пишет и через право на колонку, через вид над таблицей или
  через `PUBLIC`; умолчания прав (`ALTER DEFAULT PRIVILEGES`) не дают ей
  записи, а никому из трёх ролей — `TRUNCATE` и `TRIGGER`: их получила бы
  секция, созданная позже, — до повторного `-setup-sql`;
- `esmcp` проверяет свою роль на каждом новом соединении тем же запросом, что
  и скрипт (`internal/pgrole`): не суперпользователь, никакая другая роль со
  входом не может ею стать, ничего сверх выданного ей самой (список выше,
  параметры — тоже). Не проверяет владения и CREATE: DDL SQL агента в `PREPARE`
  не исполнит. Иначе ни одного запроса: права выдают и после настройки, а база
  могла быть недоступна при запуске;
- **объекты ролей агента и сервера не доверять никому.** Скрипт отказывает,
  если роль чем-то владеет. Верное действие — посмотреть и удалить (`DROP OWNED
  BY <роль>`: скрипт выдаст права снова). Не `REASSIGN OWNED`: функция агента
  `SECURITY DEFINER` пошла бы правами нового владельца (суперпользователя — и
  агент становится им), а его оператор в схеме из пути сочли бы своим. Большие
  объекты, временные объекты сеанса и свои умолчания прав в счёт не идут: улик
  они не касаются;
- **пароли ролей сервера и отката агенту недоступны.** `esmcp` и `esundo`
  работают под другим пользователем ОС или в контейнере, файлы настроек —
  только их владельцу (`run.sh` пишет их с правами 600). Это требование, а не
  совет: агент, который прочёл `mcp.json` или `undo.json`, войдёт этой ролью и
  обойдёт всё, что выше. Роль сервера — новая, а не прежняя роль агента:
  пароль от прежней агент знает. Вход — по SCRAM: хеш MD5 годится вместо пароля;
- скрипт выполняет суперпользователь: он отзывает у `PUBLIC` обрыв сеансов и
  снимает отметки прежних версий (схему `evidence`, роль `evidence_owner`);
- через MCP-сервер транзакция без намерения не выходит: команды агента идут в
  `PREPARE` (раздел «Пределы для агента»), закрыть транзакцию сервера и
  продолжить своей им нечем;
- своих объектов ролям агента и сервера заводить нельзя: `-setup-sql`
  отказывает, если у такой роли есть `CREATE` на какой-либо схеме или в базе (PostgreSQL 14 и старше
  дают его `PUBLIC` на схеме `public`: `REVOKE CREATE ON SCHEMA public FROM
  PUBLIC`). DDL в журнал не идёт, а функция под системным именем заслонила бы
  системную (P-242);
- у каждой таблицы под записью — первичный ключ: по нему откат находит строки.
  Таблицу без него `-setup-sql` не берёт (P-253);
- `-setup-sql` не берёт и роль агента или сервера, которая через себя или любую роль,
  которой может стать (`SET ROLE`): может CREATE, TRUNCATE, TRIGGER; владеет
  таблицей; суперпользователь, REPLICATION или CREATEROLE; состоит в
  `pg_execute_server_program` или `pg_write_server_files`; может SET параметр
  уровня суперпользователя (`session_replication_role` выключает триггеры) или
  ALTER SYSTEM (P-263, P-265, P-272). Сам скрипт идёт с путём поиска
  `pg_catalog, pg_temp`: его выполняет владелец, а функция агента с точным
  совпадением типов выиграла бы у системной (P-263);
- сверка и откат идут с путём `pg_catalog`, схемы из настройки `search_path`
  (в `undo.json` и в разделе `undo` у `esmcp`, по умолчанию их нет), `pg_temp`.
  Путь роли и базы не берётся: роль меняет его себе сама. Схемы называют,
  если триггеры таблиц пишут имена таблиц и функций без схемы: без этого
  откат падает и подсказывает, что назвать. Откат отказывает, если названной
  схемы нет или если в ней CREATE может — сама или через роль,
  которой может стать, и владелец схемы может всегда — роль со входом не из
  доверенных: её функции иначе выполнились бы правами человека (так это
  формулирует сам PostgreSQL после CVE-2018-1058). Доверенные — суперпользователи,
  владелец базы, владельцы таблиц отката (их триггеры и так идут в откате) и те,
  кто может стать ролью сеанса. Владелец схемы сам по себе — не доверенный: с
  CREATE на базе агент заводит схему и с именем роли сеанса (`"$user"`). Член
  роли-владельца — в счёт. Если отказ называет роль, которой вы доверяете, —
  уберите схему из `search_path` настроек отката.
  Чего проверка не видит — того, что уже лежит в схеме: функции и операторы,
  которые недоверенная роль завела раньше, а потом отдала (`REASSIGN`). Сборщик пишет типы колонок и
  `regclass` со схемой. До захода 2 оператор агента `=(varchar, varchar)` в
  `public` выполнялся в `esundo` правами владельца (P-263); журналы,
  записанные раньше, с собственными типами без схемы откат отказывает.

| Данные возвращены оператором | — | через 30 с | через 28–35 с |
| Место к размеру таблиц | 2,1 | 0,06 | 0,06 |

В последней колонке — разброс двух прогонов: до тревог и с ними (во втором
сценарий между действием и откатом ещё ждёт сообщения у трёх получателей, а
`esundo` достаёт записи из хранилища сам, второй раз). Скорость от перехода на
один сборщик почти не изменилась: 2 секунды из 2,3 — это сама база отдаёт и
сборщик сжимает четверть миллиона изменений. Выигрыш в
другом: одна программа, нет файла, точные номера, переподключение, видимая
потеря. Память сборщика на этой транзакции — 34 МБ: части уходят в буфер по
мере готовности.

На малом прогоне (2000 счетов, 1173 изменения) тревога приходит через 0,7 с
после действия, а от действия до возврата данных оператором проходит 3–4 с. Агент свою ошибку на ста строках возвращает через MCP
за 0,2–0,6 с: в это время входят доставка записи в хранилище, метка времени,
выдача и проверка пакета, сверка и сам откат. Из 1 МБ записей там почти всё — один документ: полтора мегабайта
случайных шестнадцатеричных цифр сжимаются вдвое, строки таблиц — в десятки раз
(32 байта на изменение на большом прогоне). Данные стенда однообразны; на
настоящих сжатие будет хуже.

## Решения, которые разошлись с планом

1. **Ядро хранилища не тронуто.** Пакет по диапазону номеров не понадобился.
   Транзакция теперь занимает единицы записей, а пакет одной записи готов сразу
   после метки времени. Что части транзакции все, видно по ним самим: номера
   1..k, признак последней, счётчик изменений в итоге потока. Пакет по окну
   остаётся для аудита: он доказывает ещё и то, что других записей не было.
2. **Сборщик сначала писал файл, теперь шлёт сам.** Первый вариант (`espgtap`
   пишет файл, `escollect` его читает) не трогал код `escollect`, но стоил
   второй программы, двойной записи и ротации. Теперь `escollect` разделён на
   вход и доставку. Тесты чтения файлов (88 штук, с симуляцией) прошли без
   единой правки. Позицию базе сборщик подтверждает после `fsync` своего
   буфера, а не после ответа хранилища: простой хранилища копит буфер у
   сборщика, а не журнал у базы.
3. **Место входа лежит в буфере, а не только в слоте.** База может прислать уже
   прочитанное заново: подтверждение не дошло, или PostgreSQL до 17-й версии
   забыл подтверждённую позицию при перезапуске. Поэтому поток начинается с
   места из буфера сборщика, и то же место отсекает повторы.
4. **«Кто» — не из базы.** Три захода эталона нашли критичное в отметках:
   секрет внутри базы видели журнал, копии и роли с REPLICATION (P-322). Теперь
   «кто» — подписанная квитанция шлюза вне базы, а сборщик только наблюдает
   (DECISIONS, п. 42).

## Чего ещё нет

Пункты, которым нужен писатель каталога квитанций без ключа или подъём базы
из копии, — за границей доверия (выше): они записаны, но не чинятся
заплатками.

- Откат через MCP требует, чтобы сервер агента мог позвать команды хранилища
  (`evidencestore proof`, `stamp`) и `esverify`: в сценарии всё на одной машине.
  Хранилище на другом узле — значит, свои команды-обёртки в секции `undo`.
- Агент откатывает только действия из квитанций своего сервера. Выбора по
  каждому конфликту нет: конфликтные строки остаются как есть и перечисляются.
- Справочник (`index.jsonl`) растёт на строку на каждую транзакцию по
  названным таблицам — около 0,1 КБ у отпечатка, около 0,3 КБ у полной — и не
  ротируется. Это не улика, а удобство: без него транзакцию находят по метке
  `xid` в хранилище, только пакет по окну ждёт две минуты.
- Полные строки транзакций шлюза — персональные данные в хранилище.
  Удалить их можно по месяцу (ключ месяца), по человеку — нет.
- Большая транзакция читается из базы за один проход, и на это время пульс
  хранилищу и отправка встают. Гигабайтная транзакция может дать у хранилища
  ложную тревогу «сборщик молчит»; после неё всё выравнивается само.
- Оборванная посреди транзакции связь оставляет в хранилище её первые части без
  последней. Вреда нет (читается целая копия), но место они занимают.
- Документация продукта на английском — обзор (`docs/postgres.md`); полный
  справочник — эта страница, на русском.
- Пределы действуют только через MCP-сервер. Своей ролью агент только читает,
  и её таймауты он может снять сам. Если роли агента выдали запись после
  `-setup-sql`, такая транзакция — отпечаток, с `require_gateway` — тревога
  `not-via-gateway`, уже после фиксации. Замок частоты — на одной машине: серверы одного агента на
  разных машинах с общим файлом квитанций по сети друг друга не ждут.
- Счёт пределов за время и замок агента — по файлам каталога квитанций: кто
  пишет туда без ключа, может стереть уже прочитанные квитанции (новый сеанс
  сосчитает меньше; свои квитанции сеанс помнит) или подменить файл замка,
  пока идёт действие (следующее пройдёт разом с ним). Сами действия сборщик
  возьмёт, но предел до фиксации не сработает.
- Право CREATE, выданное агенту после `-setup-sql`, скрипт не увидит. Свои
  запросы сервера от функций агента защищены путём поиска, сверка и откат
  такую схему в пути отказывают, но DDL агента в журнал не идёт.
- Сервер упал между намерением и исходом: исход действия — `pending`, тревоги
  нет. Откат такое действие не отвергает с порога: его транзакцию сборщик мог
  взять по намерению.
- Своей ролью агент только читает, но занять все соединения базы, держать
  `ACCESS SHARE` в простаивающей транзакции (повторный `-setup-sql` ждёт его, а
  действия — за скриптом) и писать большие объекты (`lo_from_bytea`) он может:
  `CONNECTION LIMIT` и `idle_in_transaction_session_timeout` роли агента —
  на совести оператора, а большие объекты в хранилище не идут.
- Команды, которая сверяет строку из бэкапа с отпечатком, нет: только рецепт
  хеша (выше) и пачка из хранилища (`evidencestore proof`, `esverify -body`).
- Справочник отпечатков ложится с пачкой: в первую минуту после правки
  `esundo check` по её xid отвечает «нет в справочнике» (и говорит почему).
- Откат вставки читает таблицы, которые ссылаются на неё (`ON DELETE CASCADE`):
  если таких нет в `tables`, роли отката нужен `SELECT` на них, иначе отказ
  «permission denied».
- Тип колонки в схеме, где у роли сервера нет USAGE (расширения в схеме
  `extensions`): `undo_apply` отказывает «permission denied for schema».
- SQL агента идёт ролью сервера: умолчание `ALTER ROLE … SET role = …` для неё
  не действует, сервер входит с `role = none`.
- Тип `money`: если `lc_monetary` у сборщика и у отката разный, образ
  читается не тем числом. Не закреплено и не проверено: на этой машине только
  локали C.
- SQL агента идёт в транзакции действия: всё, что он в ней изменил, —
  действие этого агента, так и задумано. Выдать своё изменение за откат или
  положить ложный отказ, как с отметками прежних версий, он не может:
  намерение и исход пишет и подписывает шлюз, вне базы.
- Готовых правил тревог и панелей для Prometheus нет: только страница
  показателей.
- Тревога об отказе приходит через доли секунды: квитанции сборщик дочитывает,
  когда поток из базы молчит. Место, до которого тревоги подняты, он хранит
  (`receipts.json`): после перезапуска они не повторяются, кроме падения между
  тревогой и записью места.
- Тревоги не ложатся в хранилище как записи: доказательства «система
  предупредила тогда-то» пока нет. Файл тревог не ротируется.
- Почты и других каналов нет: Telegram, Slack-совместимый веб-хук и свой адрес.
  В Slack текст тревоги — без разметки: `&`, `<`, `>` — сущностями, упоминания
  всех (`@channel`, `@here`) разорваны (P-254). У Mattermost и Rocket.Chat своя
  разметка (Markdown): её текст тревоги не экранирует.
- DDL посреди транзакции, значения не в UTF-8: откат отказывает или не умеет.
  Первичный ключ сборщик читает из каталога в момент чтения журнала.
- Таблица с виртуальной генерируемой колонкой (PostgreSQL 18+) под запись не
  берётся: `-setup-sql` отказывает и называет колонку.
- Секция, созданная после настройки базы, остаётся без неё, пока скрипт
  `-setup-sql` не выполнят снова: сборщик называет такую секцию при
  подключении (тревога `identity`), откат её правок отказан.
- Откат смены ключа: чужая строка, которая после транзакции сослалась на
  новый ключ, уйдёт за ним (`ON UPDATE CASCADE`) или потеряет ссылку
  (`ON UPDATE SET NULL`). При уборке вставленной строки такое ловится (ниже),
  при смене ключа — нет.
- `pgoutput` отдаёт транзакцию после фиксации: тревога о массовом изменении в
  обход MCP-сервера приходит, когда оно уже сделано. До фиксации останавливает
  только предел строк, и только действия через MCP-сервер.
- Через MCP-сервер агенту доступны только `SELECT`, `INSERT`, `UPDATE`,
  `DELETE`, `MERGE` и `VALUES`: DDL, `DO`, `CALL`, `COPY` не идут. Так
  задумано: транзакцию ведёт сервер. Агенту, которому нужна схема, нужен
  другой путь.
- `SELECT` может позвать функцию, которая сама меняет данные. Такие изменения
  в той же транзакции и входят в счёт строк; что функции вообще доступны —
  решают права роли сервера.

## Чего не проверял

- MCP-сервер говорил только со своим клиентом (`mcp_call.py`, ревизия
  2026-07-28) и с тестами прежнего рукопожатия. С настоящим агентом — нет.
- Настоящие Telegram и Slack. Отсюда до них сети нет: формат запросов сверен с
  их документацией и проверен на местном приёмнике, живого сообщения не было.
- Вход открытым паролем: код есть, живого прогона не было. TLS (`require`,
  `verify-full`), SCRAM и MD5 проверены на живой базе 22.11.
- Реплики и переключение на реплику, большие транзакции под нагрузкой (на
  стороне базы они декодируются с диска). Подъём из копии проверен на одном
  кластере (`TestLiveRestored*`, копия каталога, и тесты второго захода:
  журнал поднятой базы ушёл за место сборщика, снимок работающей базы).
  Не закрыто: поднятая база записала после подъёма только то, чего поток не
  шлёт (таблицы не из публикации), и её журнал и номера транзакций ушли за
  место сборщика — тогда подъём не виден ни при подключении, ни в потоке, и
  намерение действия, которого сборщик не успел прочесть до подъёма, может
  решить чужую транзакцию с тем же номером. Так же — база прежней истории,
  перезапущенная после последней транзакции, прочитанной сборщиком, и только
  потом поднятая из копии: отметка запуска в намерениях её последнего запуска
  позже границы. Подъём, когда сборщик с прошлого подъёма ничего не прочёл, а
  поднятую базу просто перезапустили, не отличить от второго подъёма —
  действия до перезапуска ложатся отпечатком. Слот с `failover`
  (PostgreSQL 17+) не гонялся.
- Docker: клиент MCP, которому дана команда `docker compose run … esmcp`,
  может запускать контейнеры — значит, и прочесть ключ шлюза
  (`--entrypoint cat … /state/mcp/esmcp.key`) и права root на машине. Агенту с
  шеллом под пользователем клиента MCP ключ доступен; не проверялось.
- Версии PostgreSQL: живые тесты, сценарий и откат на двух открытых базах
  прошли 22.11 на 14.25, 15.20, 16.15, 17.12, 18.7 и 19.0 (FINDINGS, раздел от
  22.11). Кластер с данными заказчика и под нагрузкой — нет. Правки P-239…P-241
  (расширенный протокол, `PREPARE`, `DISCARD ALL`, счёт строк) и P-242…P-254
  (первый заход проверки 22.11) и P-257…P-268 (второй) гонялись только на
  16.15: живые тесты и три варианта `run.sh`; P-269…P-275 (третий), роли
  сервера, агента и отката (DECISIONS, п. 39) и правки захода 1 после
  пересмотра (P-276…P-288, п. 40) — так же. На 14 и 15 роль с CREATEROLE
  может сама выдать себе членство в роли сервера: проверки видят только
  членство, которое уже есть, — не гонялось.
  `transaction_timeout` (PostgreSQL 17+) не гонялся: в своих настройках сервер
  его сбрасывает, при входе не закрепляет (параметр есть не у всех версий). Отказ `-setup-sql` по праву `CREATE` на 14-й версии
  виден только чтением кода (на 15+ у `PUBLIC` этого права нет).
- Несколько источников в одном процессе проверены сценарием (два источника) и
  тестом разбора настроек; остановка одного источника при работающих
  остальных — только чтением кода.
- CI на GitHub для этой ветки не шёл: он запускается на запросах слияния.

## Что показал первый опыт (wal2json)

Его скрипты, включая `undo.py`, с которого переписан откат, — в истории ветки
(коммиты 427d74a и b1ed565). Оттуда остаются в силе:

- `TRUNCATE` и `DROP TABLE` по журналу не вернуть. Теперь они закрыты агенту
  правами; владелец таблиц по-прежнему может, и это вне журнала.
- Таблицам нужен `REPLICA IDENTITY FULL`.
- Уничтожение ключа месяца делает до-образы нечитаемыми, а места не освобождает.
